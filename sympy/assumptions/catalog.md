# sympy/assumptions — Catalog

> Part of [SymPy](../catalog.md). Assumption system for declaring and querying properties of symbols (positive, integer, etc.).

## Python Files

| File | Summary |
|------|---------|
| `__init__.py` | Package entry point; re-exports `AppliedPredicate`, `Predicate`, `AssumptionsContext`, `assuming`, `Q`, `ask`, `register_handler`, `remove_handler`, and `refine`. |
| `ask.py` | **The authoritative location for predicate *definitions*, semantic meaning, domain restrictions, and edge-case behavior** — if a question asks *what a predicate means*, *how it is defined*, or *why* a specific input yields a particular result (e.g., why negative integers are not prime, or why imaginary inputs return False for irrational), the answer is here, not in `handlers/`. Defines the `AssumptionKeys` class (the `Q` object) with all supported predicate keys — each predicate's docstring documents its precise semantic constraints, logical relationships between predicates, and edge cases. Covers number-theory predicates (e.g., `Q.prime` is defined as requiring a natural number greater than 1, so negative integers like `-3` return `False`; `Q.composite` requires a positive integer with at least one non-trivial divisor, so boundary values like `composite(0)`, `composite(1)`, and `composite(2)` all return `False` — 2 is the smallest prime and has no divisors other than 1 and itself; `Q.even`/`Q.odd` for parity), numeric predicates (e.g., `Q.irrational` is defined as a *real* number that cannot be expressed as a ratio of integers — this domain restriction to reals means `Q.irrational(I)` returns `False` even though the imaginary unit is not rational; `Q.nonzero` requires realness, so `Q.nonzero(I)` is False while `~Q.zero(I)` is True; similarly `Q.nonpositive` vs `~Q.positive` differ for complex numbers; `Q.nonnegative` vs `~Q.negative` also differ — `Q.nonnegative(x)` requires `x` to be real and not negative (i.e., `Q.zero(x) | Q.positive(x)`), so `Q.nonnegative(I)` is `False` even though `~Q.negative(I)` is `True`), and matrix predicates (e.g., `Q.diagonal`, `Q.upper_triangular`, `Q.lower_triangular`, `Q.fullrank`, `Q.square`, `Q.symmetric`, `Q.orthogonal`, `Q.unitary`, `Q.positive_definite` — the docstrings define how predicates interrelate — including implication chains such as orthogonal → invertible (a matrix satisfying M^T M = I is necessarily non-singular), unitary → invertible, and diagonal ↔ upper-triangular ∧ lower-triangular; **the docstring examples also document shape-dependent edge cases**: non-square matrices (e.g., 2×3) automatically return `False` for predicates that require squareness such as `Q.orthogonal`, `Q.unitary`, and `Q.positive_definite` — this behavior is documented with worked `ask()` examples in the predicate docstrings here, not in `handlers/matrices.py`). Each predicate's docstring includes worked `ask()` examples demonstrating cross-predicate inferences — e.g., the `diagonal` predicate shows that querying diagonality given both lower- and upper-triangular assumptions returns `True`, illustrating how the system determines that satisfying both triangularity conditions implies only main-diagonal entries; conversely, the `triangular` predicate is defined as a *disjunction* (union) of two specific shape predicates — `Q.triangular(X)` returns `True` if `X` is EITHER lower-triangular OR upper-triangular, with docstring examples confirming both `ask(Q.triangular(X), Q.upper_triangular(X))` → `True` and `ask(Q.triangular(X), Q.lower_triangular(X))` → `True` — this union *definition* lives here in `ask.py`, not in `handlers/matrices.py` which only contains evaluation dispatch logic. Also defines the `ask()` function that queries expressions against assumptions using registered handlers, the `ask_full_inference()` function that performs **dual satisfiability checks** — it tests whether the proposition conjoined with known facts is unsatisfiable (→ False), then whether the negation conjoined with known facts is unsatisfiable (→ True), returning None (indeterminate) if both are satisfiable — this is the fallback inference method used when simpler dict-based lookups are inconclusive, and the `_extract_facts()` helper which recursively extracts facts relevant to a specific symbol from compound logical assumptions — it applies De Morgan's law to negated conjunctions/disjunctions, filters out `None` sub-results for `And` (conjunctions) while requiring all sub-results present for other connectives (`Or`, etc.). **Critically, this file also contains `get_known_facts()`, which assembles the complete static knowledge base of logical entailment rules between predicates as a single `And(...)` conjunction of `Implies` and `Equivalent` statements** — e.g., integer implies rational, rational implies algebraic, zero implies even, diagonal implies symmetric, orthogonal implies positive-definite, upper-triangular ∧ lower-triangular implies diagonal, fullrank ∧ square implies invertible, etc. This conjunction is the human-readable *source of truth* for all inter-predicate entailment relationships; `ask_generated.py` contains the machine-compiled CNF and dict forms derived from it. **This is the authoritative source for what each predicate *means* — including domain restrictions and edge cases (e.g., whether negative integers count as prime)**; look in `handlers/` for the resolution *implementation* logic that evaluates these predicates on specific expression types. |
| `ask_generated.py` | Auto-generated file (via `bin/ask_update.py`) containing the **compiled/encoded forms** of inter-predicate entailment rules, derived from `ask.py::get_known_facts()`. Provides two functions: `get_known_facts_cnf()` returns all known facts as a single `And(...)` of `Or(Not(...), ...)` clauses in Conjunctive Normal Form — this is where specific logical deduction rules are *concretely encoded* for the SAT solver in `satask.py`, including both simple two-literal implications (e.g., `Or(Not(Q.diagonal), Q.lower_triangular)` encoding diagonal → lower-triangular) and compound multi-literal deduction rules as three-or-more-way disjunctions (e.g., `Or(Not(Q.lower_triangular), Not(Q.upper_triangular), Q.diagonal)` encoding that simultaneously satisfying both triangular orientations entails diagonal). `get_known_facts_dict()` returns a precomputed transitive-closure dict mapping each predicate to the set of predicates it implies. **If the question is about where a specific entailment rule is stored/encoded for the inference engine, this file contains the actual encoded data**; for the human-readable source definitions and semantic reasoning behind the rules, see `ask.py`. |
| `assume.py` | Core infrastructure for the assumption system: `AssumptionsContext` (set of active assumptions), `AppliedPredicate` (a predicate applied to an expression — its `__new__` constructor contains argument-handling edge cases, notably a special branch that skips `_sympify` conversion when the argument is a native Python `bool`, since there is no Basic type for True/False yet; this is the place to look for questions about how predicate expressions handle non-symbolic argument types), `Predicate` (including `Predicate.eval` which resolves truth values by walking the expression type's MRO across registered handler *classes* and raises on conflicting results — this dispatches to handler classes, not SAT inference rules), global assumptions store, and the `assuming` context manager. This is where direct resolution dispatch happens — not in `satask.py` (SAT-based) or `handlers/` (individual handler logic). For inheritance-aware aggregation of SAT-based *inference rules* (logical propositions) registered against expression types and their superclasses, see `sathandlers.py::ClassFactRegistry`. For predicate *definitions* and semantic meaning, see `ask.py`; this file handles the *construction* and *infrastructure* of predicate expressions. |
| `refine.py` | Implements `refine()`, which simplifies expressions using assumptions, along with specialized refinement handlers for `Abs`, `Pow`, `exp`, `Q.real`, `atan2`, `Piecewise`, and sign. |
| `satask.py` | SAT-based assumption querying via `satask()`: converts a proposition and assumptions into a satisfiability problem and iteratively gathers all relevant known facts to determine truth values. This is a *secondary* satisfiability pathway invoked by `ask()` (in `ask.py`) only when both direct handler resolution and `ask_full_inference()` (the dual satisfiability check in `ask.py`) are inconclusive. For the simpler dual satisfiability check strategy (test proposition, then test its negation), see `ask.py::ask_full_inference`. |
| `sathandlers.py` | **The authoritative location for validating whether logical property queries (predicate expressions) are bound or unbound to symbolic targets.** The central class `UnevaluatedOnFree` (a `BooleanFunction` subclass) enforces in its `__new__` constructor that a predicate expression must be either entirely unbound ("free" — e.g., `Q.zero`, `Or(Q.positive, Q.negative)` with no target expression) or uniformly bound to a single expression ("singly applied" — e.g., `Q.zero(x)`, `Or(Q.positive(x*y), Q.negative(x*y))` where all predicates target the same expression); it raises `ValueError` for mixed cases (some predicates applied, some free) and for multi-target cases (predicates applied to different expressions like `Or(Q.positive(x), Q.negative(y))`). On valid free input it remains unevaluated (for later evaluation via `.rcall()`); on valid singly-applied input it extracts the unique target expression into `self.expr`, strips predicate bindings via `Transform` to produce the free form in `self.pred`, and calls `apply()` to dispatch evaluation. **This is distinct from `ask.py`'s `ask()` function** — `ask()` handles top-level querying and inference, while `UnevaluatedOnFree` handles the structural validation and normalization of predicate logic expressions used within the SAT inference pipeline. Subclasses `AllArgs`, `AnyArgs`, `ExactlyOneArg` vectorize predicates over expression `.args`; `CheckOldAssump` bridges to the old assumption system. Also defines `ClassFactRegistry`, the inheritance-aware handler registry for SAT-based inference rules: its `__getitem__` method iterates over *all* registered keys and unions in rules from any key that is a superclass of the queried class (via `issubclass` checks) — this is how a subclass automatically inherits inference rules registered against its parent classes. This is distinct from `assume.py::Predicate.eval`, which walks an expression type's MRO to dispatch to handler *classes*; `ClassFactRegistry` instead aggregates *SAT inference rules* (logical propositions) by scanning registered keys for superclass relationships. See `handlers/common.py` for the separate `TautologicalHandler` that evaluates logical connectives during direct (non-SAT) queries. |
| `handlers/__init__.py` | Package init for assumption handlers; re-exports `AskHandler`, `CommonHandler`, `AskCommutativeHandler`, `TautologicalHandler`, and `test_closed_group`. |
| `handlers/calculus.py` | Query handlers for calculus-related predicates (`finite`, `infinite`) that determine boundedness of expressions built from `Add`, `Mul`, `Pow`, `Symbol`, and special constants. The `AskFiniteHandler.Pow` method contains the authoritative logic for whether an exponentiation is bounded: it compares the absolute value of the base to unity (|base| ≤ 1 vs |base| ≥ 1) combined with the sign of the exponent (positive vs negative) to decide boundedness — e.g., |base| ≤ 1 with positive exponent → bounded, |base| ≥ 1 with negative exponent → bounded, unbounded base with nonzero exponent → unbounded. This is the only location for finiteness/boundedness evaluation of `Pow` — `handlers/order.py` handles sign predicates on `Pow`, not boundedness. |
| `handlers/common.py` | Base handler classes: `AskHandler` (abstract base), `CommonHandler` (always-true/false helpers), `AskCommutativeHandler`, and `TautologicalHandler` (evaluates compound logical connectives — `And`, `Or`, `Not`, `Implies`, `Equivalent` — using three-valued logic where indeterminate/`None` truth values are propagated: conjunction short-circuits on `False` but accumulates `None`, disjunction short-circuits on `True` but accumulates `None`, implication is reduced to `~p | q`). Also provides `test_closed_group` for checking closure under an operation. This is where the *logical connective evaluation* happens during a query; `satask.py` is a separate SAT-based pathway. |
| `handlers/matrices.py` | Query handler *implementations* for evaluating matrix-related predicates on specific expression types (`MatMul`, `MatAdd`, `MatrixSymbol`, etc.) — determines truth values by inspecting expression structure (e.g., checking whether all factors of a `MatMul` satisfy a predicate). This file does NOT define what predicates mean, how they relate to each other, or how a predicate is conceptually defined as a union/disjunction of sub-predicates (e.g., whether `triangular` means lower OR upper triangular, whether orthogonal implies invertible) — for predicate *definitions*, semantic meaning, union/disjunction relationships, and inter-predicate logical relationships, see `ask.py`. |
| `handlers/ntheory.py` | Query handler *implementations* for number-theory predicates: prime, composite, even, and odd. Contains the evaluation logic (e.g., calls `isprime()`) but does *not* define the predicates' semantic meaning, domain constraints, or boundary-case behavior (e.g., whether negative integers are prime, or why `composite(2)` returns `False`) — for predicate definitions, edge-case documentation, and worked boundary-case examples see `ask.py`. Does *not* handle rational/irrational classification — those are in `handlers/sets.py`. |
| `handlers/order.py` | Query handlers for order-relation predicates (negative, nonnegative, nonzero, zero, positive, nonpositive, extended_real) applied to `Add`, `Mul`, `Pow`, and numeric types. These handlers *evaluate* sign/order truth values for specific expression types — they do NOT define predicate semantics, domain constraints, or the distinction between a predicate and its logical negation (e.g., why `Q.nonzero(I)` is `False` while `~Q.zero(I)` is `True` — that distinction is a *definitional* property documented in `ask.py`, not an evaluation detail in this file), and they do NOT handle boundedness/finiteness queries (those are in `handlers/calculus.py`). **Contains per-expression-type dispatch methods with short-circuit logic** — e.g., the nonzero handler for `Mul` iterates over factors checking each for nonzero-ness: if a factor is confirmed nonzero it continues, but if a factor returns `None` (indeterminate) or `False` it immediately returns that result rather than continuing, propagating uncertainty; the positive/negative handlers for `Add` check whether all summands share the same sign. This is the place to look for questions about how sign/order/vanishing queries handle products, sums, and powers of symbolic factors, including bail-out and short-circuit behavior. Note: while this file has `_number` helper methods for numerical sign evaluation, it does **not** handle set-membership queries (imaginary, real, complex, etc.) — for those, including numerical precision guards in imaginary-number checking, see `handlers/sets.py`. |
| `handlers/sets.py` | Query handlers for set-membership predicates: integer, rational, irrational, real, extended_real, hermitian, complex, imaginary, antihermitian, and algebraic. The `AskImaginaryHandler` contains a `_number` helper method that decomposes a numeric expression via `as_real_imag()`, evaluates the real part to low precision, and includes a **precision guard**: if `evalf` returns a result with precision 1 (meaning evaluation was inconclusive), it returns `None` rather than a potentially wrong boolean — this is the place to look for questions about how imaginary-number checks handle imprecise or indeterminate numerical evaluation. Also contains per-expression-type methods including `Pow` (multi-branch logic for imaginary status of powers), `log` (imaginary status of logarithms — includes a hardcoded workaround for `log(exp(I))` and `log(exp(-I))` where the general `Q.nonpositive` query on exp with imaginary arguments incorrectly returns `None`), and `exp`. Also includes `Pow` handlers that determine rationality/irrationality of exponentiation (e.g., prime base with rational exponent yields irrational), as well as rationality of transcendental functions (`exp`, `log`, `sin`, `cos`, etc.). This is the authoritative location for rational/irrational *evaluation logic* (resolving truth values for specific expression types) — not `handlers/ntheory.py`. For predicate *definitions* and *domain restrictions* (e.g., why `Q.irrational(I)` is `False` — irrational is restricted to reals), see `ask.py`. **Important**: although `AskRealHandler` here determines *whether* an expression like `I` is real, questions about *why* predicates that implicitly require realness (e.g., `Q.nonzero`, `Q.nonnegative`, `Q.nonpositive`) return `False` for imaginary/complex inputs — and why this differs from their logical negations (`~Q.zero`, `~Q.negative`, `~Q.positive`) — are answered by the predicate *definitions* in `ask.py`, not by the real-evaluation handlers here. For sign/order predicates (negative, nonpositive, positive, etc.) applied to `Pow` and other expression types, see `handlers/order.py`. |
