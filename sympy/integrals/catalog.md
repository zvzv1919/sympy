| `integrals.py` | Core `Integral` class (unevaluated integral representation) and the `integrate` / `line_integrate` entry points. The `_eval_integral` method implements the full integration pipeline: it first attempts whole-expression strategies, then splits sum integrands term-by-term and applies an ordered fallback chain to each term (power rule for linear bases → rational function decomposition → trig → Dirac delta → singularity functions → Risch → heuristic Risch). Importantly, when a term contains a big-O asymptotic remainder (order term) and integration of that remainder fails, the method immediately returns `None` (early bail-out) rather than trying other strategies — this is because no other method can handle the O() term either. Also includes guard logic that discards results from sub-methods when they return unevaluated `Integral` objects (e.g., manual mode) and fallback/fall-through behavior on failure. The `Integral` class also provides `as_sum(n, method)` for approximating a definite integral as a finite sum using rectangle-based methods (left, right, midpoint) or the trapezoid rule — this raises `NotImplementedError` for multidimensional integrals (more than one integration variable) and `ValueError` for non-definite integrals. For questions about numerical summation approximation of integrals (rectangle rule, trapezoid rule) or errors when approximating multi-variable integrals, look here rather than in `quadrature.py`. For questions about what happens when an antiderivative cannot be found for a particular term in a sum (including early abort scenarios such as failing to integrate an asymptotic O-term remainder), look here rather than in `heurisch.py` or `manualintegrate.py` — the step-by-step engine in `manualintegrate.py` uses `DontKnowRule` for unrecognized integrands but does NOT implement the early bail-out logic for order terms. |
| `risch.py` | Implementation of the Risch algorithm for transcendental function integration, including `DifferentialExtension` (which incrementally builds a tower of transcendental extensions — this is the *tower construction* phase only, not the ODE-solving phase; its exponential extension builder checks each exponential argument against the existing tower to see if it is a logarithmic derivative of a radical; when the radical degree is 1 the argument can be rewritten in terms of existing extensions, but when the degree is greater than 1 an algebraic radical would be needed, so it tries workarounds: pulling out a nonzero constant factor and retrying, or decomposing a multi-term product of exponentials and retrying — if either workaround applies the entire extension-building process is signaled to restart from scratch, but if neither applies (single term, zero constant) it raises `NotImplementedError` because the expression is inherently algebraic, e.g. exp(log(x)/2) = sqrt(x)), `integer_powers`, `splitfactor` (which recursively performs normal/special splitting factorization of a polynomial — decomposing p into p_n * p_s where p_s is special and each square factor of p_n is normal by comparing `gcd(p, Dp)` (GCD with the full tower-of-extensions derivative via `derivation()`) against `gcd(p, p.diff(t))` (GCD with the formal variable-derivative), extracting the special factor as the quotient of these two GCDs, then recursing on the remaining quotient until no special factors remain; this is NOT the same as Hermite reduction of a rational integrand), and the main `risch_integrate` driver. Also contains `NonElementaryIntegral`, a subclass of `Integral` that acts purely as a type-level certificate of nonelementarity: when the Risch decision procedure proves that a given expression has no elementary antiderivative, the impossibility is represented in the output as an instance of this class (it defines no extra methods — just `pass` — so `isinstance(result, NonElementaryIntegral)` is the canonical way to detect proven nonelementarity). For questions about how the algorithmic antidifferentiation procedure represents impossibility results in its output, look here rather than in `rde.py` or `prde.py`. The `risch_integrate` driver iterates over extension tower cases in reverse order (exponential → primitive/logarithmic → base/rational), dispatching to `integrate_hyperexponential` or `integrate_primitive` for tower extensions; at the bottom of the tower (the purely rational function base case), it notably cannot call `ratint()` directly because of a known issue with polynomial handling, and instead falls back to the general `integrate()` with `risch=False` as a workaround — this is marked with an XXX comment. For questions about what happens at the bottom layer of the extension tower in the Risch decision procedure or about the rational-function base-case workaround, look here rather than in `rde.py` (which solves sub-problems but does not contain the main driver loop). Also contains `recognize_derivative` (checks if a rational function is the derivative of another rational function, using Laurent series and squarefree factorization of the denominator) and `recognize_log_derivative` (checks if a rational function f equals dv/v for some v by computing an elimination resultant between the denominator and a modified numerator, then testing whether all roots of that resultant polynomial are integers — notably, only *real* roots are examined; complex roots are explicitly ignored per a TODO comment, meaning the function may incorrectly return True when complex non-integer roots exist). Also contains `integrate_nonlinear_no_specials`, which integrates nonlinear monomials when the set of special irreducible polynomials is empty: it runs Hermite reduction followed by residue reduction, and if the residue reduction step indicates no elementary form exists (returns False), it returns early with partial results *before* reaching the polynomial reduction phase. Contains `integrate_hyperexponential_polynomial`, which integrates Laurent-like polynomials in both positive and negative powers of a hyperexponential (exponential tower) variable: it iterates coefficient-by-coefficient from the most negative degree to the most positive degree, extracts each coefficient, and solves a first-order Risch differential equation for each term — notably, the zeroth-degree coefficient is explicitly skipped during this loop because it requires special handling outside the per-coefficient ODE framework. Also contains `integrate_primitive_polynomial`, which integrates a polynomial p in k[t] where t is a primitive (logarithmic) monomial: it uses an iterative while-loop that peels off the leading term at each step — extracting the leading coefficient, dropping to the next lower extension level via `DecrementLevel`, calling `limited_integrate` (from `prde.py`) to find an antiderivative of that coefficient, constructing a partial antiderivative `q0`, subtracting Dq0 from p (which reduces p's degree by at least one), and accumulating q0 into the running result q. If the leading coefficient's antiderivative cannot be expressed in closed form at the lower level (i.e., `limited_integrate` raises `NonElementaryIntegralException`), the loop terminates early and returns `(q, p, False)` indicating that the remainder has no elementary integral. For questions about iterative degree reduction when integrating univariate polynomials in a logarithmic extension variable within a differential field tower, or about what happens when a leading coefficient has no elementary antiderivative at a lower tower level, look here rather than in `rde.py` (which solves the Risch Differential Equation Dy + fy = g as a sub-problem but does not contain integration drivers or degree-reduction loops). Also contains `integrate_primitive` for integration of primitive (logarithmic) extensions using Hermite reduction, residue reduction, and polynomial integration (calling `integrate_primitive_polynomial` for the polynomial part). For questions about how antiderivatives of Laurent-like expressions (both positive and negative powers of an exponential extension variable) are computed term-by-term, or why the zero-degree term is skipped, look here rather than in `rde.py`. For the related but distinct check of whether a function is the logarithmic derivative of a *radical* in a differential extension tower (using rational rather than integer root conditions), see `prde.py` instead. For solving Risch differential equations as sub-problems (including weak normalization), see `rde.py`. For questions about what happens when the coefficient b in a first-order linear ODE Dq + b*q = c is detected to be a logarithmic derivative during the cancellation phase of solving, see `cancel_primitive` in `rde.py` rather than looking here — `DifferentialExtension.__init__` checks logarithmic derivatives only for tower *construction*, not for ODE solving. |
| `rde.py` | Algorithms for solving the Risch Differential Equation (Dy + f*y == g), used as a sub-problem solver by the Risch algorithm. Includes `weak_normalizer`, which adjusts a rational function so that none of the residues at its finite poles are positive integers — a necessary normalization step (NOT a test for whether f equals dv/v). It does this by computing a square-free factorization of the denominator's normal part, forming a resultant polynomial in a new variable, finding the positive integer real roots of that resultant, then constructing a correction factor q as a product of GCDs so that f − Dq/q is weakly normalized. Note: `weak_normalizer` does NOT determine whether a rational function is a logarithmic derivative — it only removes positive-integer residues as a preprocessing step for the RDE solver. For the question "does there exist v such that f = dv/v?" (testing integrality of *all* roots of an elimination resultant), see `recognize_log_derivative` in `risch.py` instead. Also includes `order_at` and `order_at_oo` for computing pole/zero orders, `normal_denom` and `special_denom` for denominator decomposition of the RDE problem (these call `splitfactor` from `risch.py` as a subroutine to obtain normal/special factors, but do NOT themselves implement the recursive GCD-based splitting factorization algorithm — they use the factorization result to set up the reduced equation), `bound_degree` for degree bounds, and `spde`/`solve_poly_rde` for the polynomial-level RDE solver. For questions about how a polynomial is recursively decomposed into normal and special factors by comparing GCD with the formal variable-derivative vs. the full tower-of-extensions derivative, see `splitfactor` in `risch.py` instead. Also contains `cancel_primitive` and `cancel_exp`, the cancellation-case solvers for the Risch Differential Equation in primitive (logarithmic, constant-derivative) and hyperexponential extension towers respectively. `cancel_primitive` first checks (via `is_log_deriv_k_t_radical_in_field` from `prde.py`) whether the coefficient b is the logarithmic derivative of some element z in the field — if b == Dz/z (radical degree n == 1), it raises `NotImplementedError` because the required `is_deriv_in_field()` subroutine is not yet implemented; otherwise it iteratively reduces the equation degree-by-degree, solving at each coefficient level by dropping to a lower tower level and calling `rischDE`. | `prde.py` | Algorithms for solving the Parametric Risch Differential Equation (Dy + f*y == Sum(ci*gi)), paralleling the methods in `rde.py`. Also contains `limited_integrate`, which solves the *limited integration problem*: given f and auxiliary functions w1, ..., wn, determine whether f = Dv + Sum(ci*wi) for some v in k(t) and constants ci. It works by reducing the problem, setting up linear constraints via `prde_linear_constraints`, computing the `constant_system`, and then examining the dimension of the resulting nullspace to decide among three outcomes: (1) if the nullspace is empty (dimension 0), no elementary antiderivative exists and `NonElementaryIntegralException` is raised; (2) if the nullspace has exactly one basis vector (dimension 1), the first constant c1 is normalized to 1 and the problem reduces to a standard (non-parametric) Risch DE solved via `spde` and `solve_poly_rde`; (3) if the nullspace has dimension greater than 1 (or the constraint matrix is trivial), the more general `param_rischDE()` algorithm is needed. For questions about how a solver decides between "no closed-form solution," "a unique solution via a standard differential equation," and "a more general parametric algorithm is needed" when the antiderivative problem involves a linear combination of given auxiliary functions, look here rather than in `integrals.py` (which implements the top-level integration pipeline with ordered fallback chains across different integration methods, but does not contain the nullspace-dimension-based triage logic for the limited integration sub-problem). Also contains `real_imag`, a helper that separates a rational function into its real and imaginary components when evaluated at the square root of negative one, *without* performing an explicit substitution — it classifies each polynomial term's exponent modulo 4 to determine sign contributions (powers 0,1,2,3 cycle through +real, +imag, −real, −imag), then combines numerator and denominator parts via the standard complex-division formula. This is used in the hypertangent case of the parametric special denominator computation. For separating real/imaginary parts of complex logarithmic terms arising from rational-function *integration* (using resultants and conjugate root pairs), see `log_to_real` in `rationaltools.py` instead — that is a different technique for a different purpose. Also contains `is_log_deriv_k_t_radical_in_field`, which checks whether a rational function in a differential field tower is the logarithmic derivative of a *radical* (Du/u) by performing residue reduction and testing that all roots of the resultant polynomial are rational. This function handles each extension tower case differently — the exponential case calls `parametric_log_deriv` recursively, the primitive case recurses via `is_log_deriv_k_t_radical_in_field` itself at a decremented level, and the ground-level 'base' case is handled entirely differently by directly checking three necessary conditions on the denominator: (1) the denominator must be square-free, (2) the degree of the numerator must be strictly less than the degree of the denominator, and (3) the numerator and denominator must be coprime (enforced via cancellation). If any of these conditions fails, the function returns None immediately. For questions about the base-case denominator conditions required for a rational function to be the logarithmic derivative of a radical, look here rather than in `rde.py` (which contains `weak_normalizer` — a preprocessing normalization step that removes positive-integer residues but does NOT test whether f equals Du/u). For the simpler check of whether a plain rational function is a logarithmic derivative (dv/v) using integer root conditions on the resultant, see `recognize_log_derivative` in `risch.py` instead. Also contains `parametric_log_deriv_heu`, a heuristic for solving the parametric logarithmic derivative equation n*f == Dv/v + m*Dtheta/theta. This heuristic computes an LCM of denominators, applies split factorization (via `splitfactor`), and derives a common factor `z` from the GCD of the normal part with its derivative — if this `z` turns out to be an element of the constant field (i.e., does not depend on the extension variable `DE.t`), the heuristic raises `NotImplementedError` because it cannot proceed without a nontrivial divisor for the polynomial division step. For questions about what happens when the split-factorization-derived common factor is constant, or about heuristic failure modes in parametric logarithmic derivative solving, look here rather than in `risch.py`. |
| `heurisch.py` | Heuristic Risch algorithm for indefinite integration; provides `heurisch` (core algorithm) and `heurisch_wrapper` (post-processing wrapper that inspects result denominators for symbolic poles, filters out poles already present in the original integrand, and returns a `Piecewise` only for genuinely new singularities). Also contains the `components` helper for decomposing expressions into transcendental building blocks. The `heurisch` function builds a set of candidate antiderivative terms by pattern-matching subexpressions of the integrand: for half-integer power expressions (rational exponent with denominator 2), it matches the base against quadratic patterns like `a*x² + b` and `a*x² - b`, then adds inverse trigonometric or inverse hyperbolic candidate terms depending on the signs of the coefficients — e.g., for the `a*x² - b` pattern with positive `b`, it adds `acosh(...)` when `a` is positive but an `atan(...)`-based term when `a` is negative; for `a*x² + b` with positive `b`, it adds `asinh(...)` when `a` is positive but `asin(...)` when `a` is negative. Similarly, for exponential subexpressions it matches against quadratic-in-x or quadratic-in-log(x) patterns and adds `erfi`/`erf` terms based on the sign of the leading coefficient. For questions about which special candidate terms (inverse trig, inverse hyperbolic, error functions) are generated during heuristic integration based on the sign of coefficients in a quadratic base pattern, look here rather than in `manualintegrate.py` (which has its own inverse-trig rule dispatch but does not use the same heuristic candidate-term-generation approach). When the question involves avoiding unnecessary piecewise branches for division-by-zero or denominator singularities in integration results, look here rather than in `manualintegrate.py`. The `heurisch` function also defines internal helper functions `_splitter` and `_deflation` for recursively decomposing the denominator of the integrand into coprime components. `_deflation` reduces a polynomial by computing its GCD with its own formal partial derivative (gcd(q, q.diff(y))). `_splitter` recursively factors a polynomial into a (special, normal) pair: for each variable y, it computes h = gcd(q, Dq) where Dq is the formal derivation of q (the full multi-variable derivation, not just a partial derivative), then extracts s = quo(h, gcd(q, q.diff(y)), y) — the quotient of the GCD-with-derivation by the GCD-with-partial-derivative — and splits q/s recursively. This decomposition is essential for constructing the candidate antiderivative's logarithmic part. For questions about how the heuristic integration algorithm decomposes the integrand's denominator into coprime factors using GCD with the derivation vs. GCD with the partial derivative, look here rather than in `rde.py` (which contains `weak_normalizer` for removing positive-integer residues — a different normalization), `risch.py` (which contains `splitfactor` for normal/special splitting in the Risch algorithm — a related but distinct decomposition operating within a differential extension tower), or `prde.py` (whose `prde_normal_denom` calls `splitfactor` as a subroutine for parametric RDE setup but does not itself implement the recursive GCD-based coprime decomposition used in the undetermined-coefficients heuristic). |
| `manualintegrate.py` | Step-by-step integration emulating by-hand techniques, returning a tree of named rule objects (namedtuples like `RewriteRule`, `URule`, etc.); provides `integral_steps` and `manualintegrate`. The u-substitution rule (`substitution_rule`) handles potential division-by-zero in the scaling coefficient: after computing the substitution's constant multiplier `c`, it examines the denominator of `c` — if the denominator contains free symbols (parameters), it checks whether each factor of the denominator could be zero (using `fuzzy_not`), and for each potentially-zero factor, it computes an alternative integration path assuming that factor equals zero, then assembles a `PiecewiseRule` with branches for each zero-denominator case plus the normal-path default. For questions about how the step-by-step engine guards against division-by-zero in the scaling coefficient during a change-of-variable (u-substitution), look here rather than in `integrals.py` (whose `Integral.transform` method validates uniqueness of the variable mapping but does not construct piecewise results for potentially-zero denominators in the substitution coefficient). Also includes a `power_rule` function that handles expressions of the form base^exp: when the base is a constant and the exponent is the integration variable (e.g., a^x), it checks whether log(base) is zero (i.e., base == 1) using `fuzzy_not` — if definitively nonzero, it returns a standard exponential rule; if definitively zero, it returns a constant result of 1; if indeterminate (symbolic base that might or might not be unity), it constructs a `PiecewiseRule` with branches for both possibilities. | `transforms.py` | Integral transforms: Mellin, inverse Mellin, Laplace, inverse Laplace, Fourier, inverse Fourier, sine, cosine, and Hankel transforms with their unevaluated class representations and dispatch entry points. The internal Laplace transform computation integrates exp(-s*t)*f over [0, ∞), then processes piecewise convergence conditions: each disjunct is pattern-matched against argument/polar-lift forms to extract a convergence half-plane bound (abscissa) and auxiliary conditions. A two-stage filtering strategy is applied — first it keeps only conditions where both the convergence abscissa is not negative-infinity AND auxiliary conditions are not False; if that yields no candidates, it falls back to allowing negative-infinity abscissa (requiring only that auxiliary conditions are not False). The surviving conditions are then sorted by descending abscissa and ascending complexity, and the best is selected. For questions about what happens during Laplace convergence-condition selection when every candidate has a convergence abscissa of negative infinity, look here rather than in `meijerint.py` (which handles Meijer G-function antecedent checking but not Laplace-specific convergence strip filtering). The `IntegralTransform` base class handles linearity by splitting sum-of-terms integrands, computing each term's transform independently, and then merging their convergence conditions via logical conjunction (`And`); if the merged conditions evaluate to `False` (i.e., are contradictory/unsatisfiable), the base class raises an `IntegralTransformError` — this error-handling path lives in `_collapse_extra`, not in `integrals.py`. For questions about what happens when convergence conditions from individual transform terms conflict or are contradictory, look here rather than in `integrals.py`. The Hankel transform implementation uses Bessel functions (besselj) and includes multi-branch error handling: if the integration result is not Piecewise, it raises an error; if it IS Piecewise, it extracts the first branch and checks whether that branch still contains an unevaluated Integral — if so, it raises a distinct error about "integral in unexpected form." For questions about error handling or piecewise results in Bessel-function-based integral transforms, look here. Also contains `_rewrite_sin`, a separate helper function that converts a single sine factor `sin(m*s + n)` into a pair of gamma functions compatible with a given fundamental strip (a, b). It uses the reflection formula `pi/sin(pi*x) = gamma(x)*gamma(1-x)` but must ensure the resulting gamma functions don't become undefined due to the integration contour placement — it computes an integer shift `r` via `ceiling(-m*a - n.as_real_imag()[0])` so that both gamma arguments are safely positioned within the strip, and returns `(gamma1, gamma2, fac)` with an appropriate sign factor `(-1)**r`. Notably, it deliberately avoids using the standard `re()` function to extract the real part of `n`, instead calling `n.as_real_imag()[0]`, because `re()` does not properly expand the expression — this is explicitly noted in a code comment and is a subtle correctness concern for contour shift computation. For questions about how sine-to-gamma conversion avoids producing undefined gamma functions or how the contour shift is computed for the G-function representation, look here rather than in `meijerint.py`. Also contains `_rewrite_gamma`, the central helper that converts a product of trigonometric functions, polynomial factors, and gamma functions into Meijer G-function parameters (an, ap, bm, bq) for the inverse Mellin transform's vertical-contour inversion. `_rewrite_gamma` calls `_rewrite_sin` internally for each sine/cosine factor. Before classifying factors, `_rewrite_gamma` performs pole classification within the fundamental strip: an inner function determines whether each singularity lies to the left or right of the strip boundaries. When the strip boundaries or the singularity position contain unresolved symbolic variables (free symbols) and the inequality cannot be decided, the function silently returns `None` instead of raising an error — there is even a commented-out error raise with an explicit XXX marker acknowledging this as a deliberate graceful-degradation choice for symbolic boundaries. For questions about what happens during pole classification when strip boundaries contain symbolic variables, look here rather than in `meijerint.py`. `_rewrite_gamma` also computes an optimal rescaling constant for the complex integration variable before factor classification: it extracts coefficients of the integration variable from all gamma-function arguments and from all trigonometric arguments (sin, cos, tan, cot), but normalizes trigonometric coefficients differently — each trigonometric coefficient is divided by pi before being added to the multiplier list, reflecting the pi-periodicity of trig functions vs. the unit-periodicity of gamma. These normalized coefficients are then combined via LCM/GCD arithmetic to find the optimal variable substitution s → s/s_multiplier. For questions about how the rescaling constant for the integration variable is determined or how trigonometric coefficients are normalized differently from gamma-function coefficients, look here rather than in `meijerint.py` (which contains `_get_coeff_exp` for extracting coefficients from Meijer G-function objects but does not perform this trig-vs-gamma normalization). `_rewrite_gamma` decomposes all trigonometric factors — sine, cosine, tangent, and cotangent — into pairs of gamma functions using the reflection formula, with contour-aware shifting to keep gamma arguments well-defined within the fundamental strip. When a gamma function's linear coefficient in the integration variable is not ±1, `_rewrite_gamma` applies the gamma multiplication theorem (duplication formula) to split it into multiple gamma factors with unit coefficient, adjusting the overall scaling factor and exponential accordingly. Polynomial linear factors are fully factored via root-finding and converted to gamma pairs as well. The actual evaluation of inverse Laplace integrals (including exponential factor extraction and shift handling) is performed in `meijerint.py`, and the Meijer G lookup table lives there too — but the trigonometric-to-gamma decomposition, sine-to-gamma-pair conversion, and multiplication-theorem normalization logic lives here in `transforms.py`. | `trigonometry.py` | Direct (non-step-by-step) integration of products of sin^n(x)*cos^m(x) via the `trigintegrate` function, which returns a closed-form antiderivative without exposing intermediate rewriting steps. Internally uses dedicated recursive helper functions for pure sin^n(x) and cos^n(x) powers that handle both positive and **negative** integer exponents. For positive n, the recursion steps downward (n−2) with base cases at n=1 and n=0. | `rationaltools.py` | Tools for integrating rational functions: `ratint`, `ratint_ratpart`, and `ratint_logpart` implementing Hermite and Lazard-Rioboo-Trager methods. These compute the actual antiderivative of a rational function (always elementary). `ratint_ratpart` implements the Hermite reduction (Horowitz-Ostrogradsky algorithm): given coprime polynomials f, g with deg(f) < deg(g), it decomposes f/g into A' + B where B has no repeated roots in its denominator. It does this by computing the GCD of g and its formal derivative g' (the derivative of the denominator polynomial with respect to x) to obtain factors u and v, then setting up undetermined-coefficient polynomials A (over u) and B (over v), forming a system of linear equations from f = A'·v − A·(u'·v)/u + B·u, and solving for the unknown coefficients. For questions about how a rational integrand is split into a derivative of a rational expression plus a remainder whose denominator has no repeated factors using the GCD of the denominator with its derivative, look here rather than in `risch.py` (which contains `splitfactor` for normal/special splitting factorization — a different decomposition). `ratint` includes automatic real/complex domain detection: when the caller does not explicitly specify a `real` flag, `ratint` inspects all atoms (sub-expressions) of the integrand — if any atom (other than the integration variable) has `is_real` equal to False, the expression is treated as complex; otherwise it defaults to real. This domain choice affects the logarithmic part of the antiderivative: in complex mode, the logarithmic terms are expressed using `RootSum` with `Lambda` (compact complex logarithms); in real mode, the logarithmic terms are converted to real-valued form using `log_to_real` (arctangent and natural logarithm). For questions about how the integration routine automatically determines whether to produce real or complex logarithmic antiderivatives, or how the `real` flag is auto-detected from the integrand's atoms, look here rather than in `risch.py`. Also contains `log_to_real` and `log_to_atan` for converting complex-valued logarithmic terms (arising from rational function integration) into purely real-valued expressions using arctangent and natural logarithm. `log_to_atan` first checks whether the numerator polynomial f has a lower degree than the denominator polynomial g — if so, it swaps them as (-g, f) before performing polynomial division, ensuring the division step is well-defined; it then recurses via the extended GCD to accumulate arctangent terms. For questions about the degree-comparison swap preprocessing or the recursive extended-GCD decomposition in the log-to-arctangent conversion, look here rather than in `meijerint.py` (which extracts coefficients and exponents from Meijer G-function objects but does not perform log-to-atan conversion). `log_to_real` substitutes t = u + iv, separates real/imaginary parts, computes resultants, finds roots filtered to real values, selects only conjugate pairs with positive imaginary part, and accumulates log/atan terms — it returns `None` if not all roots of the resultant are real (i.e., conversion to real form fails). For questions about how sums of complex logarithmic integration terms are converted to real form, or when that conversion fails, look here rather than in `meijerint.py`. For checking whether a function is the logarithmic derivative of a radical in a differential extension tower, see `prde.py` instead. |
