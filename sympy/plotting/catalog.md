# sympy/plotting — Catalog

> Part of [SymPy](../catalog.md). 2-D and 3-D plotting with backends for matplotlib, pyglet, and text-based output.

## Python Files

| File | Summary |
|------|---------|
| `__init__.py` | Package init that re-exports the public plotting API: `plot`, `plot_parametric`, `plot3d`, `plot3d_parametric_line`, `plot3d_parametric_surface`, `plot_implicit`, `textplot`, and `PygletPlot`. |
| `plot.py` | Core plotting module defining the `Plot` class, data series classes (`LineOver1DRangeSeries`, `Parametric2DLineSeries`, `SurfaceOver2DRangeSeries`, `ParametricSurfaceSeries`, `ContourSeries`, etc.), backend classes (`BaseBackend`, `MatplotlibBackend`, `TextBackend`), and the public convenience functions `plot`, `plot_parametric`, `plot3d`, `plot3d_parametric_line`, and `plot3d_parametric_surface`. Also contains `_arity`, a Python 2/3 compatibility helper for counting how many arguments a callable accepts: on Python 2 it uses the deprecated `inspect.getargspec`, while on Python 3 it uses `inspect.signature` and filters parameters to include only `POSITIONAL_OR_KEYWORD` kind — keyword-only, variadic (`*args`/`**kwargs`), and positional-only parameters are all excluded from the count. Line series (`Line2DBaseSeries` subclasses including `Parametric2DLineSeries`) produce output via `get_segments`, which uses an adaptive recursive subdivision algorithm: a nested `sample` function recursively bisects parameter intervals, inserting points until segments are nearly collinear or a maximum recursion depth is reached. To prevent periodic aliasing artifacts, each subdivision point is placed at a randomly jittered position (uniform random offset between 0.45 and 0.55 of the sub-interval) rather than the exact midpoint; a minimum recursion depth of 6 is enforced unconditionally, and complex/undefined values trigger denser probing with 10 intermediate points. Surface series instead use `get_meshes`, which creates parameter-space grids (via numpy `meshgrid`/`linspace`), lambdifies the symbolic expressions into callable functions (using `experimental_lambdify.vectorized_lambdify`), and evaluates them over the grids to return coordinate arrays. For example, `ParametricSurfaceSeries` (three-component parametric 3D surface over two parameters) builds u/v meshes, then applies three separate lambdified functions to produce x, y, z arrays. The 3D surface base class also provides `get_color_array`, which handles custom coloring of surfaces: when the user supplies a callable for the surface color, it introspects the callable's arity (number of arguments) using an `_arity` helper, then branches on whether the series is parametric (`is_parametric`) or coordinate-mapped — parametric series feed parameter-space variables from `get_parameter_meshes` while non-parametric series feed coordinate variables from `get_meshes`, and the number of variables passed (1, 2, or all 3) is determined by the callable's arity. This arity-based dispatch for custom color functions lives here in `plot.py`, not in `pygletplot/color_scheme.py` (which handles color mapping exclusively for the pyglet backend). `MatplotlibBackend.__init__` enforces dimensional compatibility: it raises `ValueError` if the series list mixes 2D and 3D data, and configures either a 2D axes (with zero-centered spines) or a 3D projection subplot accordingly. Also contains `check_arguments`, which validates and normalizes arguments into (expressions, ranges) tuples, assigns a default fallback interval of (-10, 10) when no range is provided, and has an explicit limitation where three-element expression groups cannot be distinguished from range tuples. Additionally contains `_matplotlib_list`, a helper that converts a list of bounding rectangular intervals into x/y coordinate lists suitable for matplotlib's `fill` command — when the interval list is empty, it appends four `None` values to each coordinate list as a workaround because matplotlib does not accept empty lists for `fill`. This bounding-rectangle-to-fill-coordinates conversion lives here in `plot.py`, not in `plot_implicit.py` (which produces the bounding rectangles via interval arithmetic but does not convert them to matplotlib fill coordinates). |
| `plot_implicit.py` | Implicit plotting using interval arithmetic (with a fallback mesh-grid sampling algorithm for rendering). Defines `ImplicitSeries` and the `plot_implicit` function for rendering equations, inequalities, and boolean combinations of two-variable expressions as filled regions. The interval-arithmetic path (`_get_raster_interval`) recursively subdivides rectangular 2D regions (not 1D parameter intervals) and tests inclusion via interval evaluation — this is fundamentally different from the 1D parametric-curve adaptive subdivision in `plot.py`. To prevent false positives for equality constraints (e.g., `y == x` incorrectly evaluating to True over an entire aligned rectangle), `_get_raster_interval` adds small random jitter to the initial grid sample points, breaking artificial alignment between x and y intervals so that only genuinely satisfying sub-regions pass the interval test — without jitter, range-based evaluation of equality conditions over axis-aligned boxes would fill rectangles instead of drawing thin curves. `plot_implicit` handles its own variable detection and range creation: it inspects free symbols, creates default ranges (-5, 5), and — when only a single symbolic variable is present — introduces a synthetic dummy variable so the expression can still be visualized as a 2D plot. Also handles boolean expression expansion, equality/inequality detection, and depth clamping. Does not use `plot.py`'s `check_arguments`. |
| `textplot.py` | Provides `textplot`, a function that renders a crude ASCII-art plot of a single-variable SymPy expression over a given interval to the terminal. |
| `experimental_lambdify.py` | Low-level internal lambdify variant that converts a single SymPy expression into a callable numerical function. Translates expression strings to use math/numpy/mpmath and handles edge cases that the standard `lambdify` does not. This is a utility consumed by the data series classes in `plot.py`; it does not orchestrate mesh/grid generation or coordinate array assembly — that responsibility belongs to each series class's `get_meshes` method in `plot.py`. |
| `intervalmath/__init__.py` | Package init for the interval math subpackage; re-exports the `interval` class and all interval-aware math functions (sin, cos, exp, log, sqrt, etc.). |
| `intervalmath/interval_arithmetic.py` | Defines the `interval` class representing a floating-point interval with a validity flag (`is_valid`). Implements arithmetic operators (+, -, *, /, **) and comparisons used by `plot_implicit` for adaptive region subdivision. The power implementation includes `__pow__` (dispatching to helper functions `_pow_int` and `_pow_float` for scalar exponents) and `__rpow__` (handling scalar-base–interval-exponent cases); `__rpow__` contains special logic for negative scalar bases: when the exponent interval has zero width it rationalizes the exponent via `nsimplify` and checks whether the denominator is even (returning invalid, since even roots of negatives are undefined in reals) or odd (computing the signed result). `_pow_float` similarly rationalizes the power to decide validity based on numerator/denominator parity. Does not implement mathematical functions (sin, cos, ceil, floor, etc.) — those are in `lib_interval.py`. |
| `intervalmath/lib_interval.py` | Implements interval-aware versions of standard math functions (exp, log, sin, cos, tan, sqrt, Abs, floor, ceil, etc.) and boolean operations (And, Or) over `interval` objects, using numpy for speed. Each function tracks validity: domain violations set `is_valid=False`, partial domain coverage sets `is_valid=None`, and discontinuity-sensitive functions like `ceil` and `floor` set `is_valid=None` when the rounded endpoints differ (indicating a step discontinuity within the range). Note: `exp` and `log` here are utility functions consumed by `interval.__pow__` in `interval_arithmetic.py` for interval-on-interval exponentiation, but all power operator logic — including `__pow__`, `__rpow__`, and the negative-base rationalization/parity checks — is defined in `interval_arithmetic.py`, not here. See `interval_arithmetic.py` for the `interval` class definition and all arithmetic operators. |
| `pygletplot/__init__.py` | Package init for the pyglet-based plotting backend; defines and exports the `PygletPlot` factory function. Documents the auto-detection logic that infers curve vs. surface rendering from the number of free variables (one = curve, two = surface) and determines the coordinate mode from the number of supplied expressions (one = rectilinear/Cartesian, two or three = parameter-driven). Also documents flexible interval syntax, curvilinear coordinate support, the indexed calculator-like interface, and keyboard controls. |
| `pygletplot/plot.py` | Implements `PygletPlot`, the main class for the pyglet backend. Its `__init__` accepts positional arguments (used to initialize a plot function at index 1) and several keyword arguments including `visible` (default `True`) and `axes` — the `axes` argument is a semicolon-delimited key-value option string (e.g., `"style=ordinate; stride=0.25; overlay=True; colored=False"`) that configures the coordinate reference-line display: style (none/frame/box/ordinate), tick spacing (stride), whether axes are drawn on top of the plot (overlay), and whether axes use per-axis RGB coloring (colored). This axes configuration is documented and initiated here in `PygletPlot.__init__`, not in `pygletplot/util.py` (which only provides the low-level `parse_option_string` utility for splitting semicolon-delimited strings into dictionaries). When visible is true, `self.show()` is called during construction, causing the plot window to appear immediately — window display is triggered here in `PygletPlot`, not in `PlotWindow`. Manages a dictionary-indexed collection of plot functions via `__setitem__`, which validates inputs and dispatches to `PlotMode`: if the argument is a `GeometryEntity`, it is explicitly wrapped in a list (even though `GeometryEntity` may satisfy `is_sequence`), ensuring geometry objects are treated as atomic items rather than unpacked as argument sequences. Also provides `__delitem__`, `firstavailableindex`, `append`, `__len__`, `__iter__`, `adjust_all_bounds`, and `wait_for_calculations` — all guarded by a reentrant render lock for thread safety. Supports interactive features like color schemes, coordinate modes, and image saving. Also defines the `ScreenShot` class, which handles all screenshot capture logic: `_execute_saving` waits a configurable number of render cycles (frame-delay mechanism) before reading OpenGL pixel data via `glReadPixels`, then uses PIL to flip the resulting image (correcting OpenGL's bottom-up orientation) and save it to disk; `save` optionally creates an invisible off-screen window for headless capture; `_create_unique_path` auto-generates sequential filenames. Note: this file is distinct from the top-level `plotting/plot.py`, which defines the matplotlib-based `Plot` class and data series; `PygletPlot` has its own independent function-management interface. |
| `pygletplot/color_scheme.py` | Defines `ColorGradient` and `ColorScheme` classes for mapping surface/curve vertex data to RGB colors exclusively in the pyglet backend. Supports user-defined color functions, named presets, and gradient interpolation. `ColorScheme._fill_in_vars` handles variable-role assignment for color schemes based on how many symbolic variables the user supplies: 1 variable → assigned to the parametric-curve slot (t), 2 variables → assigned to the two surface-parameter slots (u, v), 3 or more variables → assigned to the three spatial-coordinate slots (x, y, z) with any extras filling parametric slots; unspecified variables receive placeholder "unbound" names to prevent accidental use in expressions. This count-based variable-role interpretation for color schemes lives here, not in `pygletplot/__init__.py` (which documents curve-vs-surface auto-detection from variable count for plot mode selection, a separate concern) and not in `pygletplot/plot_mode.py` (which handles independent-variable discovery and interval population for plot modes, not color variable roles). Note: this is unrelated to the arity-based custom color callable dispatch for 3D surface data series, which is handled by `SurfaceBaseSeries.get_color_array` in the top-level `plot.py`. |
| `pygletplot/managed_window.py` | Provides `ManagedWindow`, a pyglet `Window` subclass that runs its event loop in a separate thread, serving as the base class for `PlotWindow`. |
| `pygletplot/plot_axes.py` | Implements `PlotAxes` and helper classes (`PlotAxesOrdinate`, `PlotAxesFrame`) for rendering labeled coordinate axes with tick marks in the pyglet 3-D plot window. |
| `pygletplot/plot_camera.py` | Defines `PlotCamera`, which manages the OpenGL camera (projection, rotation, zoom, panning) for the pyglet plotting window, supporting both perspective and orthographic modes. Its `apply_transformation` method *composes* translation and rotation into the modelview matrix (via `glTranslatef` + `glMultMatrixf` of the stored rotation) to position the scene for the viewer — it does not neutralize or strip rotation. To make primitives always face the camera by resetting the rotation submatrix to identity while keeping translation, see the billboard helper in `pygletplot/util.py`. |
| `pygletplot/plot_controller.py` | Implements `PlotController`, which translates keyboard and mouse input into camera rotation, zoom, and other interactive actions in the pyglet plot window. |
| `pygletplot/plot_curve.py` | Defines `PlotCurve`, a `PlotModeBase` subclass that calculates and renders 1-D parametric curves (wireframe line strips) in the pyglet backend. |
| `pygletplot/plot_interval.py` | Defines `PlotInterval`, a helper class representing a named variable range with step count, used to generate evaluation grids for pyglet plot modes. |
| `pygletplot/plot_mode.py` | Defines `PlotMode`, the grandparent class for all pyglet plot modes. Handles mode registration, lookup by alias or variable count, argument parsing, and coordinate-mode selection. Also contains initializer helper methods for variable discovery and interval population: `_find_i_vars` collects independent variables from user-supplied intervals and expression free symbols; `_fill_i_vars` copies default independent variables and overrides them with user-given ones; `_fill_intervals` copies default intervals, fills them from user input, then finds any "orphan" intervals (those with no variable assigned) and automatically assigns the next unused independent variable to each — this orphan-interval auto-assignment logic lives here, not in `plot.py`'s `check_arguments` (which only handles default range creation for the matplotlib-based API). |
| `pygletplot/plot_mode_base.py` | Defines `PlotModeBase`, the intended parent class for concrete plot modes (`PlotCurve`, `PlotSurface`). Its `_get_evaluator` method implements the evaluator-selection strategy for the pyglet 3D backend: it first attempts to create a fast compiled lambda-based numeric evaluator (via `_get_lambda_evaluator`), and if that raises any exception, it logs a warning and falls back to a slower symbolic-substitution evaluator (via `_get_sympy_evaluator`). The choice is governed by the `use_lambda_eval` flag, which is set to `True` by default unless the user explicitly passes the `use_sympy_eval` option. The concrete evaluator methods (`_get_sympy_evaluator`, `_get_lambda_evaluator`) are abstract here and implemented by the mode subclasses in `plot_modes.py` — the fallback-decision logic itself lives here in `PlotModeBase`, not in `experimental_lambdify.py` (which only provides low-level expression-to-callable conversion) and not in `plot_modes.py` (which defines what each evaluator does but not the try/fallback dispatch). Its `draw` method is the central rendering dispatcher: it reads the current visual style (a bitmask where bit 1 = filled/solid, bit 0 = wireframe/edge-outline), then conditionally executes the filled-polygon pass (`_draw_solid_display_list`, which sets `GL_FILL`) and/or the edge-outline pass (`_draw_wireframe_display_list`, which sets `GL_LINE` with polygon offset) — this bitmask-based pass selection logic lives here, not in `pygletplot/plot.py`'s `__setitem__` (which only lets the user *set* the style string but does not decide which OpenGL passes to run). Display lists are lazily compiled from callable objects stored on internal render stacks (`_draw_solid`, `_draw_wireframe`): `_render_stack_top` checks whether the top of the stack is a callable or an already-compiled list, compiling or regenerating as needed. Also provides `push_solid`/`push_wireframe` for enqueuing render functions, threaded vertex/color calculation with `Event`-based reentrant guards (`_calculate_verts`, `_calculate_cverts`), and evaluator setup. |
| `pygletplot/plot_modes.py` | Defines concrete plot modes for the pyglet backend: `Cartesian2D`, `Cartesian3D`, `ParametricCurve2D`, `ParametricCurve3D`, `ParametricSurface`, `Polar`, `Cylindrical`, and `Spherical`. Each mode provides two evaluator methods — `_get_sympy_evaluator` (using symbolic `.subs()` substitution) and `_get_lambda_evaluator` (using `lambdify` for compiled numeric evaluation). For example, `Cartesian3D._get_sympy_evaluator` (the two-variable surface z=f(x,y)) extracts the dependent variable expression and both interval variables, then returns a closure that performs sequential symbolic substitution — first substituting x, then substituting y into the result — to compute the numeric (x, y, z) triple for each input pair. Each curvilinear mode contains the explicit trigonometric coordinate-conversion formulas that transform a radius function (defined over angles) into XYZ Cartesian coordinates for rendering: `Spherical` converts (r, θ, φ) → (r·cos θ·sin φ, r·sin θ·sin φ, r·cos φ), `Cylindrical` converts (r, θ, h) → (r·cos θ, r·sin θ, h), and `Polar` converts (r, θ) → (r·cos θ, r·sin θ, 0). These coordinate conversions and symbolic evaluators live here in the mode classes, not in `pygletplot/plot_surface.py` (which iterates over intervals and calls evaluators but does not define evaluation logic), and not in the top-level `plot.py`'s `ParametricSurfaceSeries.get_meshes` (which handles numpy grid generation for the matplotlib backend). Also defines the `float_vec3` decorator, which wraps sympy-based evaluator functions to coerce their symbolic evaluation results into native Python `float` three-component tuples before they are sent to the renderer; each mode's `_get_sympy_evaluator` method uses this decorator. 2-D modes embed into 3-D space by zeroing the third component. See `plot_mode.py` for mode registration/lookup and `plot_mode_base.py` for the evaluator-setup base class. |
| `pygletplot/plot_object.py` | Defines `PlotObject`, a minimal base class for anything that can be drawn in the pyglet plot window, providing a `visible` flag and a `draw` method stub. |
| `pygletplot/plot_rotation.py` | Utility functions for computing 3-D rotation matrices from sphere-mapped screen coordinates, used for interactive trackball-style rotation in the pyglet backend. |
| `pygletplot/plot_surface.py` | Defines `PlotSurface`, a `PlotModeBase` subclass that calculates and renders 2-D parametric surfaces (wireframe and solid quad strips) in the pyglet backend. Its `_on_calculate_verts` method iterates over u/v interval sets and calls an evaluator function (obtained from `_get_evaluator`) to compute vertex coordinates, but it does not define the evaluator logic itself — the symbolic evaluators (using `.subs()`) and lambda evaluators (using `lambdify`) are defined in the concrete mode classes in `plot_modes.py` (e.g., `Cartesian3D._get_sympy_evaluator`). This is also distinct from the data-series mesh generation in the top-level `plot.py` (e.g., `ParametricSurfaceSeries.get_meshes`), which converts symbolic expressions into numpy coordinate arrays for the matplotlib backend. |
| `pygletplot/plot_window.py` | Implements `PlotWindow`, the `ManagedWindow` subclass that sets up OpenGL state, coordinates the camera and controller, and drives the per-frame drawing loop for pyglet plots. Its `draw` method serves a dual purpose: while iterating over registered graphical objects to render them (under the render lock), it simultaneously accumulates vertex and color computation progress counters — this avoids locking and iterating a second time just to collect progress statistics. Reading progress attributes from renderables is wrapped in a `try/except ValueError` to gracefully handle concurrent modification (e.g., when a background calculation thread resets progress counters mid-read); the ValueError is silently caught and the progress update is simply skipped for that frame. At a throttled interval, it passes these accumulated counters to `update_caption`, which formats and displays computation progress percentages (vertices and colors) in the window title bar. This progress-display logic lives here in the rendering loop, not in `pygletplot/plot.py`'s `wait_for_calculations` (which only blocks until calculations finish without tracking per-frame progress in the title). `PlotWindow` handles rendering mechanics only — it does not control when the window is first shown; the decision to display the window is made by `PygletPlot.__init__` in `pygletplot/plot.py` (via the `visible` flag). Its `draw` method triggers screenshot capture (by calling `ScreenShot._execute_saving`) but does not implement the capture logic itself — see `pygletplot/plot.py` for the `ScreenShot` class. |
| `pygletplot/util.py` | OpenGL and math utility functions for the pyglet backend: model/projection matrix retrieval, screen-to-model coordinate conversion (via `gluUnProject`/`gluProject`), interpolation, vector operations, and option-string parsing. Also provides a billboard matrix function that modifies the current 4×4 OpenGL modelview matrix to make drawn primitives always face the camera: it resets the upper-left 3×3 rotation submatrix to the identity while preserving the translation column and the bottom row, effectively stripping all rotational components from the current transformation. This camera-facing rendering helper lives here, not in `plot_camera.py` (which manages projection, zoom, and rotation state but does not implement billboard/sprite-facing logic). |
