| `dense.py` | `DenseMatrix` and `MutableDenseMatrix` (aliased as `Matrix`) implementations. `DenseMatrix` stores elements internally as a flat one-dimensional list (`_mat`) and provides concrete evaluation methods that operate directly on this flat storage: `_eval_trace` computes the trace by summing diagonal entries via flat-index arithmetic (`_mat[i*cols + i]`), `_eval_transpose` reorders the flat list using slice stepping (`_mat[i::cols]`), `_eval_conjugate`, `_eval_adjoint`, and `_eval_determinant`. Also provides element-wise symbolic equivalence via `equals` (three-valued: True/False/None — short-circuits on False but accumulates undecided results), structural `__eq__`/`__ne__`, and private decomposition/solve helpers (`_cholesky`, `_LDLdecomposition`, `_lower_triangular_solve`, `_upper_triangular_solve`) — these private helpers contain only the core computational algorithm with NO input validation, NO squareness checks, and NO dimension-mismatch error raising; for the public validation wrappers (`lower_triangular_solve`, `upper_triangular_solve`) that check squareness, dimension matching, and triangularity and raise `NonSquareMatrixError`/`ShapeError`/`TypeError`/`ValueError` before delegating here, see `matrices.py::MatrixBase`. `DenseMatrix` also defines all binary arithmetic operator overloads (`__add__`, `__radd__`, `__sub__`, `__rsub__`, `__mul__`, `__rmul__`, `__matmul__`, `__rmatmul__`, `__div__`, `__truediv__`) that wrap the other operand through `_force_mutable` before delegating to the parent class — this is the coercion layer that ensures operand compatibility when mixing immutable/read-only and mutable/writable matrix types in arithmetic; this is the mechanism for in-place element-wise column transformations on the flat-list-backed mutable matrix, `row_swap`/`col_swap` for swapping rows or columns in-place, and `row_del`/`col_del` for deleting entire rows or columns from the mutable flat-list storage — notably `col_del` iterates rows in reverse order (`range(self.rows - 1, -1, -1)`) when deleting entries from the flat `_mat` list to avoid index corruption caused by earlier deletions shifting subsequent positions, then decrements `self.cols`; critically, `col_del` performs bounds checking for negative indices (`i < -self.cols`) but does NOT normalize negative indices to positive values before using them in the deletion loop (no `i += self.cols` step), unlike `row_del` which both bounds-checks AND normalizes negative indices (`if i < 0: i += self.rows`) before slicing — this asymmetry means negative-index column deletion passes validation but computes incorrect flat-list offsets during the reverse-iteration deletion; `row_del` deletes a contiguous slice and decrements `self.rows`. Note: negative index normalization for general matrix element access (e.g., `__getitem__`/`__setitem__`) is handled by `matrices.py::MatrixBase.key2ij`, but `col_del`/`row_del` perform their own independent bounds checking and index handling directly on the flat `_mat` list. Also contains `_force_mutable`, a coercion utility that converts various types to mutable matrices — notably handles objects supporting the numpy array protocol (`__array__`), where zero-dimensional (scalar-like) arrays are sympified rather than wrapped in a Matrix. Note: `DenseMatrix` arithmetic methods (`__add__`, `__sub__`, `__mul__`) operate on proper Matrix objects — for raw list-of-lists arithmetic helpers (add, sub, negate, multiply) that operate on nested Python lists over a domain K, see `densearith.py` (where `sub` notably composes negate+add rather than performing direct element-wise subtraction). `DenseMatrix` does NOT contain submatrix selection by boolean masks or index lists — for `extract` (which supports boolean-list row/column selection), see `matrices.py::MatrixBase.extract`. `DenseMatrix._eval_inverse` dispatches to the actual inverse algorithms (`inverse_GE`, `inverse_LU`, `inverse_ADJ`) defined in `matrices.py`, and also supports a `try_block_diag` optimization path: when enabled, it decomposes the matrix into independent diagonal sub-blocks via `get_diag_blocks()`, inverts each block separately using the chosen method, then reassembles the full inverse via `diag(*r)` — this avoids inverting the entire matrix at once when it has block-diagonal structure. This block-diagonal inverse optimization is on the concrete `DenseMatrix` class, distinct from `expressions/matmul.py::MatMul._eval_inverse` which symbolically reverses factor order in a matrix product expression. |
| `sparse.py` | `SparseMatrix` (`MutableSparseMatrix`) backed by a dictionary-of-keys (`_smat`) storage (memory-efficient for matrices with many zero entries), with sparse-specific LIL/row-list access, Cholesky and LDL decomposition (sparse-specific implementations that validate positive-definiteness *after* computing factors by checking for `nan`/`oo` in the result matrices, raising `ValueError` if found — distinct from the dense versions in `matrices.py`), sparse-specific linear system solvers that chain factorization with triangular/diagonal substitution steps: `_LDL_solve` decomposes A = L·D·L^T then performs a three-step pipeline — forward substitution with L (`_lower_triangular_solve`), diagonal solve with D (`_diagonal_solve`), and backward substitution with L^T (`_upper_triangular_solve`); `_cholesky_solve` similarly decomposes via `_cholesky_sparse` then chains forward and backward triangular solves; the triangular solvers (`_lower_triangular_solve`, `_upper_triangular_solve`) exploit sparsity by iterating only over non-zero entries via `row_list()`, and `_diagonal_solve` divides each RHS entry by the corresponding diagonal element — these are the concrete sparse substitution-step solvers, distinct from the high-level `LDLsolve`/`cholesky_solve` wrappers in `matrices.py::MatrixBase` which delegate to dense decomposition routines, `__eq__`/`__ne__` structural equality — `__eq__` first checks shape, then for sparse-vs-sparse comparison directly compares the underlying `_smat` dictionaries; for sparse-vs-dense comparison (when the other operand is a `MatrixBase` but not a `SparseMatrix`), it converts the dense matrix to a temporary `MutableSparseMatrix` and then compares the resulting `_smat` dictionaries — this reconciles different internal representations (flat list vs dictionary-of-keys) by normalizing both to DOK format before comparison; catches `AttributeError` and returns `False` for non-matrix operands. This is distinct from `immutable.py::ImmutableMatrix._eval_Eq` which implements three-valued equality for the `Eq()` symbolic relational (returning `None` for undetermined cases), and from `dense.py::DenseMatrix.__eq__` which compares flat-list representations directly. `is_Identity` property (checks square, diagonal entries == 1, then verifies no off-diagonal nonzeros by comparing `len(self._smat)` to `self.rows` — exploits the sparse dict storing only nonzero entries), `row_join` and `col_join` for horizontal and vertical concatenation of sparse matrices — `row_join` appends columns side-by-side (`[A B]`) with a dual-path implementation: when the other operand is a dense matrix (flat `_mat` list), it iterates with a counter over the flat list and only stores non-zero values into the sparse `_smat` dict; when the other operand is itself a `SparseMatrix` (DOK format), it directly copies entries from the other's `_smat` dict with offset column indices — this dual handling preserves sparsity regardless of input format. Also `row_swap`/`col_swap` for in-place row/column swapping on the DOK dict — `row_swap` uses a two-phase approach with a temporary buffer: it iterates through sorted `row_list()` entries, immediately popping and reinserting entries for one row (j→i) but buffering the other row's entries (i) in a temporary list to avoid key collisions in the underlying `_smat` dict, then writes the buffered entries back in a second pass (i→j); includes early termination once past both target row indices; `col_swap` uses the same pattern with `col_list()`. `solve_least_squares` (computes the minimum-norm least-squares solution for overdetermined systems using the normal equations identity `(A^T A)^{-1} A^T b` in a single expression, with configurable inversion method — distinct from `matrices.py::MatrixBase.pinv_solve` which uses the Moore-Penrose pseudoinverse approach), `solve` (checks if the matrix is square before delegating to inversion — for non-square systems it raises `ValueError`: under-determined systems (rows < cols) get a plain error without suggestions, while over-determined systems (rows > cols) get a suggestion to use `solve_least_squares`; note that `matrices.py::MatrixBase.solve` has analogous dimension-checking logic but with *different* error messages — the dense version suggests `gauss_jordan_solve(rhs)` for under-determined systems and `solve_least_squares(rhs)` for over-determined systems, while this sparse version omits the alternative suggestion for under-determined cases), and `applyfunc`. Note: `sparsetools.py` handles DOK↔CSR format conversion utilities only — for actual sparse matrix concatenation/joining operations, see this file. |

| `expressions/matexpr.py` | `MatrixExpr` base class for symbolic matrix expressions, plus `MatrixSymbol`, `Identity`, `ZeroMatrix`, `MatrixElement`, and generic expression infrastructure (shape, transpose, inverse, indexing). `MatrixExpr.__getitem__` is the primary element-access method for symbolic matrix expressions — it handles three indexing modes: (1) tuple `(i, j)` indexing delegates to `_entry(i, j)` after validation; (2) slice indexing creates `MatrixSlice`; (3) single flat-integer indexing performs row-wise decomposition (`i = key // cols`, `j = key % cols`) but FIRST checks that both shape dimensions are concrete `Integer` types — if either dimension is symbolic (e.g., `Symbol('n')`), it raises `IndexError("Single index only supported for non-symbolic matrix shapes.")` because divmod cannot be evaluated on symbolic dimensions; additionally, if the single index is itself a symbolic `Symbol`/`Expr` (not an integer), it raises `IndexError("Single index only supported for non-symbolic indices.")`.
