# sympy/geometry — Catalog

> Part of [SymPy](../catalog.md). Computational geometry: points, lines, polygons, circles, ellipses, and curves.

## Python Files

| File | Summary |
|------|---------|
| `__init__.py` | Package initializer that imports and re-exports all public geometry classes (Point, Line, Ellipse, Circle, Polygon, Plane, Curve, Parabola) and utility functions. |
| `entity.py` | Defines `GeometryEntity`, the base class for all geometric objects, and `GeometrySet`, a base for entities that can also act as SymPy Sets. Provides common methods such as rotation, scaling, translation, and a base `intersection` method. `GeometryEntity._eval_subs` implements the **symbolic substitution hook** for all geometry entities: when either the old or new substitution value is a sequence (e.g., a tuple of coordinates), it wraps them as `Point3D` if `self` is a `Point3D` instance, otherwise as `Point` (2D) — this 2D-vs-3D coordinate-wrapping decision during substitution lives here in `entity.py`, not in `point.py` (which handles point construction but not substitution dispatch). Also implements `GeometryEntity.encloses(o)`, the generic containment-check dispatcher: it type-dispatches on the inner object — Points delegate to `encloses_point`, Segments check both endpoints, Ellipses verify center-inside + no-intersection + boundary-point-inside, Polygons/RegularPolygons check all vertices (with a center early-exit for regular ones) — and critically, **Rays and Lines always return False** because infinite-length objects can never be fully enclosed by a bounded figure. This enclosure/containment dispatch logic lives here in `entity.py`, not in `line.py`/`line3d.py` (which define per-entity `contains` for point-on-entity tests, a different concept). Note: subclasses (including `Point` in `point.py`) override `intersection` with their own logic and dispatch — for point-vs-non-point overlap, see `Point.intersection` in `point.py`. |
| `point.py` | Implements `Point`, `Point2D`, and `Point3D` classes representing points in n-dimensional Euclidean space, with operations like distance, midpoint, collinearity checks, concyclic testing, and coordinate transformations. `Point2D` owns the concyclic-point test: for four or more points it internally constructs a circle (from `ellipse.py`) using the first three points and checks containment of the rest — if those three points are collinear, circle construction fails with a geometry error, which is caught to return False (this edge-case handling lives here in `point.py`, not in `ellipse.py` or `polygon.py`). Arithmetic dunder methods (`__add__`, `__sub__`, `__mul__`, `__div__`, `__neg__`, `__abs__`) are defined on `Point` and perform coordinate-wise operations; `__add__` validates that both operands have matching dimensionality and raises `ValueError` (not `GeometryError`) when dimensions differ. `Point2D` and `Point3D` override `scale`, `rotate`, and `translate` from `GeometryEntity` with point-specific implementations — notably, `scale` with a reference point decomposes into translate-to-origin, scale, translate-back. `Point3D` also provides static `are_collinear` and `are_coplanar` methods — `are_coplanar` implements the coplanarity test with robust fallback logic: it takes the first two points as a base, then iterates through remaining candidates to find a third non-collinear point that can define a plane (via `Plane(a, b, c)`); if construction raises `ValueError` (because the triple is linearly dependent/collinear), it catches the error and tries the next candidate, then checks all remaining points against the successfully constructed plane. This degenerate-triple retry loop lives here in `point.py`, not in `plane.py` (which only raises the error without recovery). `Point.intersection` implements a double-dispatch pattern: for point-vs-point it checks equality (with dimension-mismatch `ValueError`), but when the other object is a non-point entity (line, segment, circle, etc.) it delegates via `return o.intersection(self)` — so the overlap logic for a point against any other geometry entity lives here in `point.py` as the dispatch entry point, not in `entity.py`. |
| `line.py` | Implements **2D** line-like entities: `LinearEntity`, `Line`, `Ray`, `Segment` (all operating in 2D Euclidean space). Supports intersection, perpendicularity, parallelism, angle computation, projections, and `coefficients` for 2D line equations. `Ray` provides `xdirection` and `ydirection` properties that report the ray's orientation along each axis as symbolic infinity (+oo, -oo) or zero (for perpendicular rays) — these are the **2D** direction properties; see `line3d.py` for the 3D counterparts (`Ray3D.xdirection`, etc.). `LinearEntity.projection` is the **2D projection method** for projecting points and linear entities onto a line: for a `Point` it finds the closest point on the line (via perpendicular intersection); for a `LinearEntity` (Segment, Ray, Line) it projects both defining endpoints individually and, critically, **if both endpoints project to the same point, returns that single Point rather than a degenerate entity** — this endpoint-collapse edge case lives here in `line.py`, not in `plane.py` (whose `Plane.projection_line` handles 3D line-onto-plane projection, a different operation). `LinearEntity.arbitrary_point` generates a parameterized coordinate representation along the entity (returns `p1 + (p2 - p1)*t`) and validates that the chosen parameter symbol does not conflict with the object's existing `free_symbols`, raising `ValueError` on collision — the same pattern used by `Ellipse.arbitrary_point` in `ellipse.py`. See `line3d.py` for 3D counterparts. |
| `line3d.py` | Implements **3D** line-like entities: `LinearEntity3D`, `Line3D`, `Ray3D`, `Segment3D`. Provides 3D-specific `contains` — notably `Ray3D.contains` uses x/y/z-direction properties to test whether a point lies in the forward half of the ray — along with `distance`, `equation`, direction ratios/cosines, and intersection/parallelism in 3D space. `LinearEntity3D.projection` is the **3D projection method** for projecting points and 3D linear entities onto a 3D line: for a `Point3D` it finds the closest point on the line (via perpendicular intersection); for a `LinearEntity3D` (Segment3D, Ray3D, Line3D) it projects both defining endpoints individually and, critically, **if both endpoints project to the same point, returns that single Point3D rather than a degenerate entity** — this endpoint-collapse edge case lives here in `line3d.py` (the 3D counterpart of the same logic in `line.py`), not in `plane.py` (whose `Plane.projection_line` handles projecting a line onto a plane, a different geometric operation). For **2D** ray direction properties (`Ray.xdirection`, `Ray.ydirection`), see `line.py`. |
| `plane.py` | Implements the `Plane` class for 3D planes, constructed from three points or a point and normal vector. `Plane.intersection` is the central dispatch for plane-vs-entity intersections: handles points, all linear entities (lines, rays, **segments** — with parametric boundary validation that returns empty when the solved point falls outside a bounded entity's extent), and plane-plane intersections (using a coordinate-substitution fallback chain: tries z=0, then y=0, then x=0 to find a point on the intersection line). Also supports distance calculations and projections. `Plane.arbitrary_point` generates a parametric point that traces a unit circle on the plane around its base point as the parameter varies 0 to 2π: for axis-aligned normals (two normal-vector components zero) it returns a direct cos/sin formula, but for the **general non-axis-aligned case** it projects a scaled trial point onto the plane and solves for the scale factor to maintain unit distance — this projection-and-solve approach for parametric plane points lives here in `plane.py`, not in `curve.py` (which handles parametric 2D curves, a different concept). `Plane.random_point` uses `arbitrary_point` with a random parameter substitution. |
| `polygon.py` | Implements `Polygon`, `RegularPolygon`, and `Triangle` classes. `Polygon.__new__` performs **vertex cleanup** during construction: first removes consecutive duplicate points, then removes collinear intermediate vertices — but critically **preserves "shared" vertices** (points appearing more than once in the input list) even if they are collinear with their neighbors, because such duplicate vertices serve as crossing points in self-intersecting or bowtie-shaped figures. This shared-point-aware collinear cleanup logic lives here in `polygon.py::Polygon.__new__`, not in `util.py` (whose `convex_hull` computes hull boundaries of point sets, a different operation that does not handle polygon vertex deduplication or shared-point preservation). After cleanup, if fewer than 4 vertices remain, the constructor degrades the result to a `Triangle`, `Segment`, or `Point`. Provides area, perimeter, centroid, angle computations, and specialized `Triangle` geometric-center properties: circumcenter (computed by intersecting perpendicular bisectors of sides), orthocenter (intersection of altitudes), incircle, circumcircle, circumradius, medians, and nine-point circle. `Polygon._do_poly_distance` implements the **rotating calipers algorithm** for computing the minimum distance between two convex polygons: it starts from extreme vertices (highest-y on one polygon, lowest-y on the other), selects initial traversal directions by comparing angles of neighboring edges against a horizontal support line (with a **distance-based tiebreaker** when both neighbors form equal angles — picking the closer neighbor), then iterates antipodal pairs comparing edge-rotation angles until returning to the start. This convex-polygon minimum-distance algorithm lives here in `polygon.py`, not in `util.py` (which provides `convex_hull`, `farthest_points`, and `closest_points` for point sets, not polygon-to-polygon distance). `RegularPolygon.area` computes the area formula using `sign(r)*n*length**2/(4*tan(pi/n))` — the `sign(r)` factor is critical because the circumscribing radius `r` may be negative in symbolic computation, and this ensures the area correctly reflects the sign rather than assuming a positive radius. `Triangle.is_similar` contains the actual algorithm for determining whether two triangles are uniform scalings of each other: it computes side lengths for both triangles and checks all six permutations of side-to-side correspondences to see if the ratios are equal (the correspondence/matching problem is solved by brute-force enumeration of permutations). `RegularPolygon` overrides `scale` and `rotate` from `GeometryEntity`: `scale` with equal x/y factors preserves the `RegularPolygon` type (scaling the radius), but asymmetric scaling (x ≠ y) degrades the result to a plain `Polygon` by expanding vertices first. |
| `ellipse.py` | Implements `Ellipse` and `Circle` classes with support for tangent lines, focal properties, eccentricity, intersection with lines and other conics, and arbitrary point generation (including parameter-symbol collision validation that raises `ValueError` when the chosen parameter name conflicts with existing free symbols). `Circle.__new__` handles **3-point construction**: when given three points, it checks collinearity via `Point.is_collinear` and raises `GeometryError` if all three are collinear (degenerate input rejection), then constructs the circle by computing the circumcenter and circumradius of the triangle formed by the three points — this collinearity guard and 3-point-to-circle construction logic lives here in `ellipse.py::Circle.__new__`, not in `point.py` (which only provides the `is_collinear` primitive without the circle-construction context). `Ellipse.__contains__` implements the **`in` operator** for ellipses with type-based dispatch: for a `Point` it substitutes coordinates into the ellipse equation and checks if it simplifies to zero (i.e., the point lies on the boundary); for another `Ellipse` it **only checks equality** (`self == o`) rather than performing true geometric containment — so `e2 in e1` returns `True` only if the two ellipses are identical, not if one is geometrically inside the other; for all other types it returns `False`. This `__contains__` / `in`-operator behavior is distinct from `GeometryEntity.encloses` in `entity.py`, which performs actual geometric enclosure testing. `Circle.intersection` contains the **circle-vs-circle intersection algorithm** with geometric edge-case handling: for two circles with different centers, it computes the inter-center distance `d` and returns an empty list when `d > R` (too far apart) **or** `d < abs(r1 - r2)` (one circle fully contains the other, so no shared boundary points); otherwise it computes 1 or 2 intersection points using perpendicular-offset geometry. This containment-during-intersection detection lives here in `ellipse.py`, not in `entity.py` (whose `encloses` is a separate generic containment-check dispatcher). For non-Circle arguments, `Circle.intersection` delegates to `Ellipse.intersection`. Note: `line.py` (`LinearEntity`) and `curve.py` (`Curve`) also provide `arbitrary_point` with the same collision-check pattern. |
| `curve.py` | Implements the `Curve` class for parametrically-defined 2D curves, supporting arc length computation, arbitrary point generation, and plotting-related methods. Note: for parametric point generation on 3D planes (unit-circle tracing with projection), see `plane.py`'s `Plane.arbitrary_point`. |
| `parabola.py` | Implements the `Parabola` class defined by a focus and directrix. Supports vertex, axis of symmetry, focal length, and equation generation for vertical and horizontal parabolas. |
| `util.py` | Utility functions for geometry operating on **point sets and mixed entities**: `intersection`, `convex_hull` (computes the convex hull of a point set), `closest_points` (sweep-line algorithm for nearest pair of 2D points — includes **rational/irrational coordinate handling**: when any point coordinate is non-rational, it dynamically redefines the internal distance function to use symbolic `sqrt` instead of `math.sqrt`, switching between numeric and symbolic computation depending on coordinate types; this distance-mode switching logic lives here in `util.py::closest_points`, not in `point.py`'s `Point.distance`), `farthest_points` (finds extremal point pairs in a point set — **not** polygon-to-polygon distance, which is `Polygon._do_poly_distance` in `polygon.py`), `are_coplanar`, `are_similar` (a thin dispatcher that delegates to each entity's own `is_similar` method — the actual similarity algorithms live on the entity classes, e.g. `Triangle.is_similar` in `polygon.py`), `centroid`, and `idiff` (implicit differentiation). `are_coplanar` is the **top-level coplanarity dispatcher** (distinct from `Point3D.are_coplanar` in `point.py`, which only handles pure-point inputs): it handles mixed-type inputs including Planes, LinearEntity3D objects, and critically **2D geometry entities** — when a 2D `GeometryEntity` (e.g. Circle, Polygon defined with 2D Points) is passed, it extracts defining points and converts them to 3D by appending z=0, then recursively checks coplanarity of the resulting 3D points. This 2D-to-3D conversion logic lives here in `util.py`, not in `point.py`. |
| `exceptions.py` | Defines `GeometryError` (a `ValueError` subclass), the custom exception for geometry module classes. Note: not all geometry errors use this — e.g., `Point.__add__` raises plain `ValueError` for dimension mismatches rather than `GeometryError`. |
