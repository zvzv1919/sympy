| `mod.py` | Implements the `Mod` function for symbolic modulo operations, following Python's sign convention for the remainder. `Mod.eval` performs extensive simplification: extracts GCD of the two operands via `gcd`/`gcd_terms`, simplifies sum-type dividends term-by-term, and handles non-Rational (floating-point) leading coefficients specially — when both dividend and divisor are products with float coefficients (e.g. `Mod(0.6*x, 0.3*y)`), extracts those coefficients via `as_coeff_Mul`, computes their remainder, and if zero, factors the divisor's coefficient out as a multiplier (yielding `0.3*Mod(2*x, y)`). | `mul.py` | Implements the `Mul` class for symbolic multiplication. Provides `Mul._eval_derivative` which implements the Leibniz product rule for symbolic differentiation of products — iterates over each factor, differentiates it while keeping all other factors unchanged, skips zero-derivative terms, and sums the results via `Add`. Provides `_eval_is_zero` which determines whether a product is zero by tracking both zero and infinite (non-finite) factors — when both a zero factor and an infinite factor coexist, returns None (indeterminate, since 0*oo is NaN) rather than True or False. `Mul.flatten` performs canonical flattening of products: when a factor is a Pow with negative numeric base and non-integer rational exponent, extracts the negative sign by adding the exponent to a running (-1) exponent tally and negating the base to positive before storing it for later combination — this is the core mechanism for canonicalizing sign/phase information during product simplification of expressions like `(-3)**(1/3)` or `(-2)**(3/4)`; similarly converts `I**r` (imaginary unit to rational power) into a half-exponent contribution to the (-1) tally; extracts GCD of integer bases raised to rational exponents and recombines them (e.g. `2**(1/3)*6**(1/4)` → `2**(7/12)*3**(1/4)`), resolves accumulated fractional exponents on negative unity into sign flips (only during product flattening of `a*b*c` sequences — modular-arithmetic simplification of repeated imaginary-unit factors in `(a*b)**n` power-base expansion is handled exclusively in `power.py`), and handles infinity/zoo coefficient simplification. Provides `Mul._eval_evalf` for numerical evaluation of products — includes a special branch when the leading coefficient is negative one: if the remaining expression after extracting -1 is itself a Mul, delegates to `AssocOp._eval_evalf` and negates; if the remainder is a single non-Mul term (e.g. a symbolic function like `-sin(1)`), calls `_eval_evalf` on that term directly and negates. Does not handle sign canonicalization between `{e, -e}` (see `Expr.could_extract_minus_sign` in `expr.py`). |

| `numbers.py` | Numeric types hierarchy: `Number`, `Integer`, `Rational`, `Float`, `AlgebraicNumber`, and singleton constants (`Zero`, `One`, `Half`, `NegativeOne`, `Infinity`, `NegativeInfinity`, `ComplexInfinity`, `NaN`, `ImaginaryUnit`, `Pi`, `Exp1`, `GoldenRatio`, `Catalan`, `EulerGamma`). `Integer.__new__` implements instance caching via the module-level `_intcache` dictionary: converts input to Python `int` first (normalizing external numeric types like `numpy.int32` or `numpy.int64`), then returns the cached instance if one already exists for that value, avoiding duplicate symbolic Integer objects for the same numeric value. **This is the authoritative location for all number-type `_eval_power` methods** — every concrete numeric class defines its own `_eval_power` here for type-specific exponentiation dispatch (not in `power.py`). The `Number` base class provides `as_coeff_Mul` (extracts coefficient from a numeric value as a product — has a zero edge case: when the number is zero/falsy, returns `(S.One, self)` placing zero in the remainder rather than the coefficient, instead of `(self, S.One)`; also handles the `rational` flag for non-Rational numbers) and `as_coeff_Add`. The `Number` base class also defines `__mul__`/`__add__`/`__sub__` as direct two-operand arithmetic operators (Python `*`, `+`, `-`) on Number instances — these are the base numeric type's product/sum/difference operators, distinct from `Mul.flatten`/`Add.flatten` which canonicalize multi-factor symbolic products/sums; `Number.__mul__` explicitly handles infinity operands: finite*Infinity returns signed infinity based on the finite value's sign, zero*Infinity returns NaN, and Tuple operands return NotImplemented to prevent scalar-container multiplication. `_eval_power` implementations: `Zero._eval_power` returns self for positive exponents, ComplexInfinity for negative exponents, NaN for non-real (complex) exponents, and for product-form exponents strips the leading numeric coefficient — returning zoo**terms when the coefficient is negative and self**terms otherwise; `Integer._eval_power` simplifies integer-to-fractional-exponent by factoring the integer base into primes, extracting perfect roots from the prime factorization (e.g. `(2**12)**(1/10)` → `2*(2**2)**(1/10)` by divmod of each prime's exponent by the root denominator), reducing remaining exponents by their shared GCD, and also branches on whether a negative exponent's denominator is 1 vs. greater than 1 to handle sign differently; `ComplexInfinity` returns NaN for zero/itself exponents, zoo for positive, zero for negative; `Infinity`/`NegativeInfinity` handle sign-dependent power results — `Infinity._eval_power` handles non-real numeric exponents by extracting the real component via `re(expt)`: positive real part yields ComplexInfinity, negative yields Zero, zero yields NaN; `NegativeInfinity._eval_power` checks exponent parity for positive integers: odd exponents yield -oo, even exponents yield +oo; `NegativeOne._eval_power` returns I**p when the rational exponent has denominator exactly 2 (e.g. (-1)**(3/2) → I**3), and for general rational exponents decomposes via divmod into integer and fractional parts and recurses; `ImaginaryUnit` uses mod-4; `Rational._eval_power` handles negative-base negative-exponent cases by inverting the fraction and factoring out (-1) raised to the fractional part, and for positive rational bases with rational exponents splits into numerator and denominator powers. `Rational` implements its own ordering comparison operators (`__gt__`, `__ge__`, `__lt__`, `__le__`) that use cross-multiplication for rational-vs-rational, mpf comparison for floats, and for symbolic real-valued operands clears the denominator by transforming `p/q > expr` into `p > q*expr` before delegating to `Expr`. Infinity types (`Infinity`, `NegativeInfinity`) implement their own arithmetic operators (`__add__`, `__sub__`, `__mul__`, `__div__`) that override the `Number` base class versions — these perform type-preserving dispatch: when the other operand is a `Float`, the result is returned as `Float('inf')` or `Float('-inf')` rather than the symbolic singletons `S.Infinity`/`S.NegativeInfinity`; when the other operand is a non-Float `Number`, the symbolic singleton is returned. `Infinity.__mul__` and `NegativeInfinity.__mul__` each handle zero specially: both exact zero (identity check) and floating-point zero (equality check in the Float branch) return NaN, but the dispatch path differs — exact zero is caught by an early identity check before the Float branch. They also implement their own ordering comparison operators (`__lt__`, `__le__`, `__gt__`, `__ge__`) that override `Expr`'s versions — `NegativeInfinity.__lt__` distinguishes finite/nonnegative comparands (returns true) from negative-infinite comparands (returns false), while `NegativeInfinity.__le__` simply returns true for any real; `Infinity` mirrors this with inverted logic. These type-specific operators take precedence over `Expr.__lt__` etc. `Float` implements its own ordering comparison operators (`__gt__`, `__ge__`, `__lt__`, `__le__`) with an asymmetry: `__gt__`/`__ge__` check `other.is_comparable` before numerically evaluating, while `__lt__`/`__le__` check `other.is_real and other.is_number` instead — these different conditions determine when the right-hand operand is evaluated via `evalf()`. `Float.__eq__` implements equality comparison that short-circuits to False when the other operand is an irrational `NumberSymbol` (like pi or E), preventing false positives from numerical precision matching. `NaN` distinguishes structural equality (`__eq__` returns True for `nan == nan` via identity check) from mathematical equality (`_eval_Eq` always returns False, so `Eq(nan, nan)` is False). `Float` also provides `epsilon_eq` for approximate equality comparison with a configurable tolerance. Also provides `Float.__mod__` which preserves precision when the divisor is a non-integer `Rational` (e.g., `2/3`) by first converting the Float to an exact Rational, performing the modulo in exact arithmetic, and only then rounding the result back to the original Float precision — avoiding floating-point precision loss. Also provides per-type arithmetic dunders (`__divmod__`, `__rdivmod__`, etc.) with error handling for non-convertible operands, plus `igcd`, `ilcm`, `comp`, and `mod_inverse`. |
| `operations.py` | Defines `AssocOp` (abstract base for associative operations like Add and Mul), `LatticeOp` (abstract base for algebraic lattice join/meet operations like AND, OR, Max, Min, Union, Intersection — with an absorbing element ("zero") and identity element), and the `ShortCircuit` exception class used by `LatticeOp.__new__` to immediately return the absorbing value: during argument filtering in `_new_args_filter`, encountering the absorbing element raises `ShortCircuit`, which the constructor catches to short-circuit and return the absorbing value without processing remaining operands. `AssocOp._new_rawargs` reconstructs an associative operation from raw arguments without full re-evaluation — a fast path that skips flattening but includes a safety mechanism for commutativity: if the original expression was non-commutative, commutativity is recomputed (via `_from_args`) unless the caller explicitly passes `reeval=False`. `AssocOp._matches_commutative` is the core pattern-matching engine for commutative associative operations (Add/Mul): separates pattern arguments into "exact" parts (concrete sub-expressions without wildcards) and "wild" parts (containing Wild/WildFunction placeholders), subtracts exact parts from the target expression, then attempts to match the remaining wild parts against the residual. `AssocOp._eval_evalf` handles numerical evaluation of sums/products by splitting into numeric-independent and dependent parts — includes a recursion guard that skips the split when the extracted numeric-independent part is itself an AssocOp Function, falling through to a generic per-arg evaluation path to prevent infinite recursion. |
| `power.py` | Implements the generic `Pow` class for symbolic exponentiation (construction, canonicalization, and evaluation dispatch). `Pow.__new__` performs auto-simplification of negative bases with integer exponents: when the base has a negative coefficient and the exponent is an even integer, the negative sign is stripped from the base; when the exponent is odd, a factor of -1 is extracted (e.g. `(-x)**2 → x**2`, `(-x)**3 → -(x**3)`). Does NOT contain `_eval_power` methods for concrete number types — all number-specific power evaluation (Integer, Rational, NegativeOne, Zero, Infinity, ImaginaryUnit, etc. raising to various exponent types) is in `numbers.py`. Provides multinomial expansion of sums raised to integer powers `(a+b+...)**n` via `_eval_expand_multinomial` — includes an efficient algorithm for expanding integer powers of complex numbers `(a+b*I)**n` when both real and imaginary parts are rational, using binary exponentiation (repeated squaring) on integer-converted numerators with denominator factoring to handle non-integer rational components. Provides `_eval_transpose`, `_eval_adjoint`, and `_eval_conjugate` methods for Pow expressions — `_eval_transpose` checks `base.is_complex` first (returning the expression unchanged for complex/scalar bases since transpose of a scalar is itself) and only wraps the base in transpose when the exponent is integer, differing from `_eval_adjoint`/`_eval_conjugate` which check `base.is_positive` instead of `base.is_complex`. Also provides power-base expansion that distributes an exponent over a product of factors `(a*b*c)**n → a**n * b**n * c**n`, including special handling for repeated imaginary-unit factors in the base: counts occurrences modulo 4 and reduces them (e.g., two imaginary units become -1, which is absorbed into existing negative factors when possible). Also separates commutative base factors into nonnegative, negative, and other categories to correctly handle sign distribution under non-integer exponents. `Pow._eval_evalf` handles numerical evaluation of power expressions — includes a special case for negative exponents with non-real bases: rewrites using the conjugate (`base.conjugate() / |base|^2`) and negates the exponent to avoid precision issues with complex-valued negative-power evaluation. Also provides `integer_nthroot` and `isqrt` integer root utilities. Overrides `is_constant(*wrt)` with Pow-specific logic: when the base equals zero, re-evaluates `b**e` with current assumptions (in case the original was unevaluated) and recursively checks constancy on the new form; when the base is constant and non-zero but the exponent varies, returns False; falls back to checking whether the exponent equals zero. |
| `relational.py` | Relational comparison classes: `Relational` base, `Equality` (Eq), `Unequality` (Ne), `StrictLessThan` (Lt), `LessThan` (Le), `StrictGreaterThan` (Gt), `GreaterThan` (Ge). | `rules.py` | Defines the `Transform` class, an immutable dictionary-like wrapper around a callable function with an optional filter predicate controlling membership. `__getitem__` raises KeyError when the predicate fails, `__contains__` delegates to the predicate, and `get()` provides safe retrieval with a default value. Used as a generic transformation/replacement rule. |
| `singleton.py` | Singleton mechanism: `SingletonRegistry` (accessed as `S`) and the `Singleton` metaclass that ensure unique instances of frequently used objects like `S.Zero`, `S.One`, `S.Half`. `SingletonRegistry.__getattr__` implements deferred/lazy instantiation: classes are registered during import into a pending dictionary, and actual object creation is deferred until first attribute access — on first lookup, `__getattr__` instantiates the class, installs the result as a real attribute via `__setattr__` (so subsequent lookups bypass `__getattr__` entirely), and removes the class from the pending dictionary. |
| `symbol.py` | Defines `Symbol`, `Wild`, and `Dummy` symbolic variable classes, plus the `symbols` and `var` convenience functions for bulk symbol creation. `var` creates symbols via `symbols()` and injects them into the caller's global namespace — for `Basic` instances it uses `.name` as the variable name, but for `FunctionClass` instances (e.g., when `cls=Function` is passed) it uses `.__name__` instead; a recursive `traverse` helper handles nested tuples of mixed types. `Wild.matches` implements pattern-matching for placeholder variables: rejects a candidate expression if it contains any sub-expression in the `exclude` list, then rejects if any callable in the `properties` list returns False for the candidate; only if both checks pass does it accept the match and update the replacement dictionary. `Wild.__call__` raises `TypeError` to prevent accidentally invoking a wildcard placeholder symbol as if it were a callable function — since Wild symbols resemble callable patterns but are not functions, calling one with arguments is always an error. |
