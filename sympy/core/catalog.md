# sympy/core — Catalog

> Part of [SymPy](../catalog.md). Core symbolic engine: basic objects (Symbol, Number, Expr, Add, Mul, Pow), caching, evaluation, and compatibility.

## Python Files

| File | Summary |
|------|---------|
| `__init__.py` | Package entry point; re-exports all public core classes (Symbol, Expr, Add, Mul, Pow, Number, etc.) and exposes singleton constants like Catalan, EulerGamma, and GoldenRatio. |
| `add.py` | Implements the `Add` class for symbolic addition, including canonical ordering, flattening of nested sums, and the `_unevaluated_Add` helper. Also provides `Add._combine_inverse(lhs, rhs)`, which computes `lhs - rhs` but treats operands as symbols for the purpose of infinity arithmetic — specifically, when both sides are positive infinity (`oo`) or both are imaginary infinity (`oo*I`), it returns `S.Zero` instead of `NaN`; this deliberate symbolic-level override means `Add._combine_inverse(oo, oo) == 0`, whereas `Infinity.__sub__` in `numbers.py` would produce `nan` for the same numeric subtraction — the inverse-combination logic for addition operands lives here on `Add`, not in `numbers.py` (which provides the raw numeric dunder methods on `Infinity`/`NegativeInfinity`). Also provides `Add.primitive`, which extracts the greatest common rational factor (as a `Rational` content) from a summation's coefficients using integer GCD of numerators and LCM of denominators — with special handling for `ComplexInfinity` terms: when any term is `zoo`, it filters out terms with zero denominators from the GCD/LCM computation to avoid division-by-zero, and preserves those terms unchanged in the output; this Add-specific rational-content extraction with infinity handling lives here, not in `exprtools.py` (`_gcd_terms` handles bulk GCD-of-terms computation with a different convention) or `expr.py` (`Expr.primitive` is the base-class fallback). Also provides `Add._eval_subs`, which handles substitution of partial subsets within a sum — e.g., `(a+b+c).subs(b+c, x)` yields `a+x` by detecting that the substitution pattern's terms are a subset of the sum's terms and reconstructing the result from the remaining terms; it also handles negated patterns (e.g., replacing `-b-c` with `x` in `a+b+c+d`) by negating both the replacement and the coefficient adjustment, and handles rational coefficient offsets (e.g., `(2+a).subs(3+a, y)` yields `-1+y`). This partial-sum substitution matching lives here, not in `operations.py` (which provides generic `AssocOp` pattern matching) or `basic.py` (which provides the general `subs` entry point). |
| `alphabets.py` | Defines the `greeks` tuple containing the names of the 24 Greek letters used for symbol rendering. |
| `assumptions.py` | Assumption system machinery: `StdFactKB`, `ManagedProperties` metaclass, and the `BasicMeta` metaclass that attach `.is_*` assumption attributes (e.g. `is_real`, `is_integer`) to symbolic objects. Also defines `_assume_rules`, the master set of implication/equivalence rules encoding the mathematical property hierarchy (e.g., integer→rational→real→complex→commutative, zero→even&finite, prime→integer&positive, irrational==real&!rational, etc.). The actual rule *definitions* live here; `facts.py` only provides the compilation/inference engine (`FactRules`/`FactKB`) that consumes them. |
| `backend.py` | Backend selector that imports core symbols from either SymEngine (if `USE_SYMENGINE=1`) or SymPy itself, providing a unified interface for downstream modules. |
| `basic.py` | Defines `Basic`, the root base class for all SymPy objects, with core infrastructure for args storage, the `atoms(*types)` method for extracting leaf-level components filtered by type (when no types are given, returns true atomic objects — symbols, numbers, number symbols; when types are given, filters by `isinstance` check; crucially, when an argument is an *instance* rather than a *class*, e.g. `expr.atoms(S(1))`, it implicitly converts via `type(t)` — so `atoms(S(1))` filters by type `One` finding only `1`, while `atoms(S(2))` filters by type `Integer` finding all integers; this implicit instance-to-type conversion and its subtle consequences for singleton number types live here, not in `expr.py`), substitution (`subs` method, including a `simultaneous=True` keyword that uses dummy-variable placeholders to defer all replacements until the end, preventing intermediate evaluations from collapsing expressions — e.g., `(x/y).subs([(x,0),(y,0)])` gives `0` sequentially but `nan` with `simultaneous=True` because both replacements happen at once yielding `0/0`; this deferred-replacement logic lives here, not in `exprtools.py` or `expr.py`; `subs` also handles sympification of replacement pairs internally — when a replacement value is a non-string Python object that cannot be sympified, the entire substitution pair is silently dropped rather than raising an error; when it is a string that cannot be sympified, it is converted to a `Symbol`; this substitution-time error handling lives here in `subs`, not in `sympify.py`), traversal, pattern matching, and canonical comparison. Also provides `rcall`/`_recursive_call` for recursively applying arguments through an expression tree (with a special guard that returns plain symbolic variables unchanged instead of invoking them, to prevent accidental transformation into undefined functions), and `_compare_pretty` for display-oriented term ordering (ensures big-O / asymptotic `Order` terms always sort last, and compares power expressions by exponent via pattern matching). These expression-tree call and display-ordering utilities live here on `Basic`, not in `function.py`, `expr.py`, or `add.py` — in particular, display-oriented term comparison (big-O terms sorting last) is here, not in `expr.py` (which provides the expression-level `sort_key` override for canonical ordering, a different mechanism). Also provides `Basic.sort_key`, the canonical ordering key method for all symbolic objects — it constructs a composite tuple from `(class_key(), (len(args), recursive sort keys of args), S.One.sort_key(), S.One)`, using an inner helper that recursively calls `sort_key` on `Basic` instances but passes through non-`Basic` arguments unchanged; this is the root sort-key implementation that `Expr.sort_key` in `expr.py` overrides with expression-specific branching; `default_sort_key` in `compatibility.py` is a separate standalone function for sorting arbitrary Python objects that lack a `sort_key` method. Also provides the module-level `_aresame` function for checking structural identity (not mathematical equality) of two expressions — it walks both expression trees in parallel using `preorder_traversal` and `zip_longest`, comparing both value and type at each node, so e.g. `Float(2.0)` and `Integer(2)` are structurally different even though they are mathematically equal. This structural-identity check lives here, not in `numbers.py` or `expr.py`. Also provides `Basic.doit(**hints)`, the main method for forcing evaluation of lazy/unevaluated mathematical objects (integrals, sums, limits, products) — when the `deep` hint is True (default), it recursively calls `doit` on all sub-expressions before reconstructing the result; when `deep=False`, it returns `self` unchanged without descending into child terms, allowing callers to prevent recursive evaluation; individual object types can be excluded via additional hints. This lazy-object evaluation with depth control lives here on `Basic`, not in `operations.py` (which provides `AssocOp.__new__` with `evaluate=False` for construction-time evaluation bypass — a different mechanism: `evaluate=False` prevents simplification during *construction*, while `doit(deep=False)` prevents recursive *post-hoc evaluation*) or `evaluate.py` (which provides context managers for toggling global evaluation). Also defines the `Atom` class (parent for atomic/leaf expressions like Symbol, Number) with simple `matches`, `xreplace`, and `doit` implementations. |
| `cache.py` | Caching facility providing the `cacheit` decorator and a global `CACHE` registry; uses `fastcache` when available, falling back to `lru_cache`. |
| `compatibility.py` | Python 2/3 compatibility layer providing unified imports for `string_types`, `integer_types`, `range`, `reduce`, `exec_`, `with_metaclass`, `lru_cache`, `ordered`, and other cross-version utilities. Also provides the backported LRU cache internals: `_make_key` (the cache key builder that optimizes for calls with a single positional argument of a primitive type — when there's exactly one arg whose type is in `fasttypes` (int, str, frozenset, NoneType) and `typed` is False, it returns the raw argument directly instead of wrapping it in a `_HashedSeq`, avoiding tuple/hash overhead for the common single-argument case), `_HashedSeq` (a list subclass that pre-computes and caches its hash value for use as a dict key), and the `lru_cache` decorator itself; these LRU cache key-building internals live here, not in `cache.py` (which provides the `cacheit` decorator that selects between `fastcache` and this backported `lru_cache`). Also provides `as_int`, a strict integer coercion function that converts a value to a builtin `int` and then verifies equality with the original — raises `ValueError` for non-integral inputs like irrational numbers or non-integer floats (e.g., `as_int(sqrt(10))` fails). This strict numeric-to-integer conversion lives here, not in `sympify.py` or `numbers.py`. Also provides `default_sort_key`, a universal sorting key function that produces structured tuple keys for any object — including plain Python types like integers, strings, dicts, and sets that have no `sort_key` method — enabling canonical cross-platform ordering of mixed symbolic/non-symbolic collections; for `Basic` instances it delegates to their `sort_key` method (defined in `basic.py`), but for non-symbolic objects it handles them directly (sympifying non-string items, falling back to string-based keys for unrecognized types); note that the key provides platform-consistent canonical ordering but explicitly does NOT sort by expression complexity (number of operations, variable powers), so `sin(x)*cos(x)` may sort before `sin(x)` — this universal-but-not-complexity-aware sorting lives here, not in `basic.py` (which only defines `sort_key` for symbolic objects). |
| `containers.py` | Symbolic container classes `Tuple` and `Dict` that subclass `Basic`, enabling SymPy-aware tuples and dictionaries with support for substitution and sympification. `Dict` is a concrete stored-value dictionary (not lazily computed); for a dictionary-like mapping whose values are computed on-the-fly by a callable with optional key-filtering predicates, see `rules.py` (`Transform`). |
| `core.py` | The core's core: defines `ordering_of_classes` for canonical class-level type ordering and the `BasicMeta` metaclass with `__cmp__`, `__lt__`, `__gt__` methods that compare *types* (not expression values) based on their position in that list — when both types are present in the list, their list indices determine order; when one is present and the other is not, the listed one sorts first; when *both* types are absent from the list, `BasicMeta.__cmp__` falls back to lexicographic comparison of class names (using `(n1 > n2) - (n1 < n2)`). Also defines the `Registry` base class used by the singleton mechanism and `all_classes`, a global set tracking all classes created with `BasicMeta`. Note: this module handles *class-level type ordering* (metaclass comparison), not expression-value ordering — for expression-level sort keys, see `Basic.sort_key` in `basic.py` and `Expr.sort_key` in `expr.py`. Note: `call_highest_priority` in `decorators.py` dispatches binary operators by instance-level `_op_priority` attributes, which is a different mechanism from `BasicMeta.__cmp__`'s class-level type ordering. |
| `coreerrors.py` | Defines core exception classes: `BaseCoreError` and `NonCommutativeExpression`. |
| `decorators.py` | Core decorators including `deprecated` (deprecation warnings), `_sympifyit` (auto-sympification of method arguments), and `call_highest_priority` (operator dispatch by instance-level `_op_priority` attributes — this dispatches which object's method to call during binary operations, NOT the canonical class-level type ordering which is in `core.py` via `BasicMeta.__cmp__` and `ordering_of_classes`). |
| `evaluate.py` | Provides the `evaluate` and `distribute` context managers and their backing `global_evaluate`/`global_distribute` flags to toggle automatic expression evaluation on/off. This module only controls whether evaluation happens at all — it does NOT provide a protocol for user-defined objects to register custom transformation or expansion strategies (that protocol, `_eval_expand_hint()`, lives in `function.py` under the `expand()` function). |
| `evalf.py` | Adaptive numerical evaluation engine using mpmath; implements `EvalfMixin`, the `N()` function, and internal helpers for arbitrary-precision floating-point arithmetic (e.g., `evalf_pow` for power expressions, `evalf_mul` for products). Note: construction of Float objects from strings/numbers (including string normalization and precision detection) is in `numbers.py` (`Float.__new__`), not here; this module handles evaluation of existing symbolic expressions to numerical values. Note: converting exact rationals to decimal floats while preserving integer exponents (`nfloat`) is in `function.py`, not here; `evalf.py` provides the low-level mpmath evaluation that `nfloat` calls internally via `.n()`. Note: computing order of magnitude of a numeric value (the `_mag` helper, which falls back to multi-precision `mpf_log` when Python's `math.log10` overflows) is in `expr.py`, not here. |
| `expr.py` | Defines `Expr`, the base class for algebraic expressions, providing arithmetic operators, series expansion, differentiation hooks, `as_numer_denom`, `as_coeff_Add/Mul`, `extract_multiplicatively` (attempts to cleanly divide out a factor — for Add requires ALL terms to be divisible, returning None if any single term fails; for Mul only needs ONE factor to be divisible; for Pow subtracts exponents), `extract_additively`, and many expression-analysis methods. The extract_multiplicatively/extract_additively factor-extraction logic lives here on Expr, not in `add.py` or `mul.py`. Includes `sort_key` (expression ordering key generation, with special branching for Dummy placeholders vs other Atom types), `is_constant` (constancy checking via numerical evaluation and differentiation, with a defensive assertion that numeric expressions must have no free symbols), and `_diff_wrt`. Also provides `args_cnc`, which decomposes a product (Mul) into [commutative factors, non-commutative factors] while maintaining ordering — by default splits a leading negative number like -2 into [-1, 2] (controlled by `split_1` flag), and optionally returns commutative factors as a set with duplicate detection. This commutative/non-commutative factor separation lives here on `Expr`, not in `exprtools.py` or `mul.py`. Also provides `coeff`, which extracts the coefficient of `x**n` from an expression — when the overall expression is commutative it uses set-difference matching on canonical factors; when extracting a non-commutative target from a commutative expression, it immediately returns zero; when `n=0` and both self and x are sums, it uses a recursive approach: first computes the first-power coefficient, then subtracts out those terms to get the zeroth-power remainder (rather than a direct filter); for non-commutative expressions, it can return the left or right coefficient by searching for the target subsequence in factor lists, first checking common prefix/suffix across all addends, then falling back to single-term matching — when multiple individual terms contain the target factor but no common prefix/suffix exists across all terms, it returns zero rather than attempting an ambiguous extraction. This per-expression coefficient extraction logic (including the commutative set-difference approach and non-commutative subsequence search) lives here, not in `exprtools.py` (which handles bulk GCD-of-terms computation, not single-expression coefficient extraction). Also provides `as_coefficient`, which separates an expression into a product of a given factor and a factor-free coefficient — internally it calls `extract_multiplicatively` and then checks `r.has(expr)` to verify the extracted remainder doesn't still contain the target factor nested inside composed functions (e.g., `2*sin(E)*E` as_coefficient of `E` returns None because `sin(E)` still contains `E`); returns None if not cleanly separable. These coefficient-extraction methods live here, not in `exprtools.py`. Also provides `as_independent`, which separates an expression into parts dependent/independent of given symbols — for Add it sifts terms, for Mul it sifts commutative factors and then handles non-commutative factors by stopping at the first dependent nc factor and grouping all subsequent nc factors as dependent (preserving ordering constraints). This dependency-separation logic lives here on `Expr`, not in `mul.py` or `add.py`. Also provides `primitive`, which extracts the greatest positive Rational that can be factored non-recursively from every term of an expression (treating self as an Add) — when the expression is zero/falsy, it returns `(S.One, S.Zero)` (factor=1, remainder=0) rather than `(S.Zero, S.Zero)`; this positive-rational-content extraction lives here on `Expr`, not in `exprtools.py` (`_gcd_terms` handles bulk GCD-of-terms computation and returns `(Zero, Zero, One)` for zero inputs, a different convention). Also provides base-class fallback implementations of `as_coeff_add` and `as_coeff_mul` (lowercase) that handle dependency-independence splitting for generic (non-Add/non-Mul) expressions. Also provides `Expr.powsimp`, a thin convenience wrapper that delegates entirely to `sympy.simplify.powsimp` for combining/simplifying power expressions — it does NOT split products raised to powers into individual powers (that is `expand_power_base` in `function.py`, which also handles the edge case that additive terms/sums in the base are left untouched). Also provides `_eval_is_positive` and `_eval_is_negative`, the base-class sign-determination methods for symbolic numeric values — they first attempt low-precision numerical evaluation (`_eval_evalf(2)`), split into real/imaginary parts, and check the sign; when the numerical evaluation yields no significant digits (precision == 1) and the expression is algebraic (not involving `Function`), they fall back to computing the `minimal_polynomial` from `sympy.polys.numberfields` — if the minimal polynomial is a bare symbol (meaning the value is a root of `x`, i.e., zero), they return `False` for positivity/negativity; this algebraic-fallback sign checking using minimal polynomials lives here on `Expr`, not in `evalf.py` (which provides the low-level numerical evaluation engine) or `assumptions.py`. Also defines `AtomicExpr` and `UnevaluatedExpr`. Also provides the module-level `_mag(x)` helper function that computes order of magnitude (returns integer `i` such that `.1 <= x/10**i < 1`) — it first tries Python's `math.log10`, and when that raises `OverflowError` or `ValueError` (e.g., for extremely large symbolic floats), falls back to multi-precision `mpf_log` computation; includes an off-by-one correction check. This order-of-magnitude helper lives here at the end of `expr.py`, not in `evalf.py`. Note: expression-level sort keys live here; class-level type ordering is in `core.py`. |
| `exprtools.py` | Tools for manipulating large commutative expressions: `gcd_terms`, `_gcd_terms` (helper that computes GCD of a sum's term components, returning `(content, numer, denom)` — returns `(Zero, Zero, One)` when all inputs are zero/falsy), `factor_terms`, `factor_nc`, `Factors` (sparse exponent-map representation of products with `mul`/`div`/`quo`/`rem` operations) and `Term` (efficient `coeff*(numer/denom)` representation that decomposes a product into scalar coefficient, positive-exponent factors (numerator), and negative-exponent factors (denominator), with normalization that extracts primitive content from Add bases — `Term.__init__` strictly requires commutative input and raises `NonCommutativeExpression` for non-commutative expressions; decomposition of products into coefficient/positive/negative-exponent parts lives here, not in `mul.py`), and monotonic-sign analysis. Also provides `decompose_power` and `decompose_power_rat`, which split a power expression into (base, integer_exponent) or (base, rational_exponent) — when the exponent is a product of a rational coefficient and a symbolic term (e.g., `x**(2*y/3)`), it extracts the integer numerator as the exponent and folds the rational remainder into the base (yielding `(x**(y/3), 2)`); when the exponent is numeric but non-rational (e.g., an irrational float), they fall back to returning the whole expression as base with exponent 1. This power-decomposition logic lives here, not in `power.py`. Note: `decompose_power` only extracts the integer/rational exponent from a power expression for use in GCD/factoring algorithms — it does NOT extract a rational numerical *prefactor* (content) from a power expression (e.g., extracting 9 from `3**((5+y)/2)`); that rational-prefactor extraction from powers is `Pow.as_content_primitive` in `power.py`. Also provides `_mask_nc`, which replaces non-commutative objects with placeholder symbols so commutative-only algorithms (like polynomial factoring) can be applied — when there is exactly one nc entity it is replaced with a commutative placeholder, but when multiple exist they are kept as non-commutative placeholders and the caller must handle ordering. This nc-masking logic lives here, not in `mul.py`. `Factors.div` handles division of factored power representations, including a fallback for symbolic exponents: when clean additive extraction fails, it splits exponents into numeric (`as_coeff_Add`) and symbolic parts for partial cancellation. GCD-of-terms computation and term-level arithmetic live here, not in `add.py`. This exponent-map arithmetic lives here, not in `power.py`. Note: per-expression coefficient extraction (e.g., extracting the coefficient of a factor from a sum) and commutative/non-commutative factor separation of a single product are in `expr.py` (`coeff`, `as_coefficient`, `args_cnc`), not here; this module handles bulk term-level GCD and factored-representation arithmetic. |
| `facts.py` | Rule-based deduction system: compiles alpha (single-premise) and beta (conjunction/multi-condition) implication rules and performs runtime inference via `FactRules` and `FactKB` for the assumption system. Key compilation step is `apply_beta_to_alpha_route`, which folds multi-condition (AND-based) beta rules into single-premise alpha implication chains using a fixed-point loop — when all conjuncts of a beta rule are already derivable from a single trigger, the beta's conclusion is absorbed into that trigger's alpha chain. Also provides `rules_2prereq` for building reverse prerequisite mappings. The rule compilation and folding logic lives here; the actual mathematical property rule *definitions* (e.g., integer→rational→real→complex→commutative) are in `assumptions.py`, which passes them to `FactRules` for compilation. |
| `function.py` | Implements `Function`, `FunctionClass`, `Application`, `WildFunction` (wildcard pattern-matcher for functions — its `matches` method checks whether an expression is a callable `Function`/`AppliedUndef` with matching argument count, returning `None` for non-callable expressions like plain symbols or numbers), `Lambda` (whose `__eq__` performs alpha-equivalence: it renames the other lambda's bound parameters to match self's before comparing bodies, so two anonymous callables with different parameter names but identical structure are considered equal — this semantic-equality check for anonymous functions lives here, not in `basic.py`'s `dummy_eq`), `Derivative`, `Subs`, the top-level `diff()` utility function (which first tries calling `f._eval_diff()` on the input object and, when that raises `AttributeError` because the object doesn't implement a custom differentiation hook, falls back to constructing a `Derivative` object — this dispatch-with-fallback mechanism lives here, not in `expr.py`), the main `expand()` function (the central algebraic distribution/expansion entry point — it recursively walks expression trees applying expansion hints like `mul`, `log`, `power_base`, etc.; user-defined symbolic objects can register custom expansion strategies by defining `_eval_expand_hint()` methods, where each method is responsible only for expanding its specific hint at the top-level expression, and `expand()` itself handles recursion into subexpressions when `deep=True` — the object never recurses into its own args; objects must be rebuildable by their args, i.e. `obj.func(*obj.args) == obj`; this expand protocol and the `_eval_expand_hint()` API live here, not in `evaluate.py` which only toggles automatic evaluation on/off), all `expand_*` helpers (including `expand_complex`, which decomposes a symbolic expression into its real and imaginary components by invoking only the complex expansion hint with all other hints disabled — this is the function for separating re/im parts without performing distribution, power splitting, or other algebraic simplifications; this operation-counting logic lives here, not in `expr.py`), and `nfloat` (converts Rationals to Floats in expressions while preserving integer exponents by default; when the `exponent` flag is True, it must post-process integer exponents in Pow nodes manually because `Pow._eval_evalf` special-cases Integer exponents and skips converting them — this workaround lives here, not in `evalf.py`). The `expand_power_base` wrapper distributes exponents over product factors (e.g. `(a*b)**n → a**n * b**n`) but deliberately leaves additive terms (sums) untouched — `((x+y)*z)**2` becomes `z**2*(x+y)**2`, not fully expanded. This power-base splitting logic lives here (delegating to `Pow._eval_expand_power_base` in `power.py`), not in `mul.py`. Defines the framework for both defined and undefined symbolic functions. Note: recursively applying arguments through an expression tree (`rcall`/`_recursive_call`), including the special guard that returns plain symbolic variables unchanged to prevent transformation into undefined functions, is in `basic.py`, not here; `Application.__new__` handles instantiation of function applications, not recursive expression-tree calling. `Subs` (unevaluated substitution) validates that no variable appears more than once in the substitution list (raises `ValueError` for duplicates) and handles placeholder symbol naming collisions in its `__new__` constructor — it generates underscore-prefixed `Symbol` placeholders for each substitution point value and, when a generated placeholder conflicts with an existing free symbol in the expression that maps to a different point value, iteratively prepends additional underscores until no clash exists (e.g., `_0` → `__0` → `___0`). This deferred-substitution collision-avoidance logic lives here, not in `symbol.py` (Dummy), `expr.py`, or `basic.py`. |
| `logic.py` | Internal propositional logic primitives (`And`, `Or`, `Not`, `Logic`) and fuzzy logic helpers (`fuzzy_and`, `fuzzy_or`, `fuzzy_not`, `_fuzzy_group`, `_torf`, `fuzzy_bool`), primarily used by the facts/assumption engine. `_fuzzy_group` implements tri-state group evaluation: returns True if all args are True, False if any are False (and none are None), and None if any arg is None — but with a `quick_exit` mode where encountering a *second* False returns None instead of False (modeling cases like "one transcendental among rationals means not rational, but two makes it indeterminate"). `_torf` is simpler: returns True/False only if all args are unanimously True/False, else None immediately on any disagreement. `fuzzy_bool` maps values to True/False/None (non-boolean truthy values become None). These tri-state logic utilities live here, not in `facts.py` (which provides the rule compilation/inference engine). |
| `mod.py` | Implements the `Mod` function for symbolic modulo operations, following Python's sign convention for the remainder. |
| `mul.py` | Implements the `Mul` class for symbolic multiplication, including flattening, canonical ordering, coefficient extraction, product expansion (`_eval_expand_mul` with non-commutative factor wrapping into `Basic` containers for correct distribution over addition), symbolic pattern matching (`matches`/`_matches`/`_matches_simple` — `_matches` handles negative-one prefix splitting: when the pattern splits via `as_two_terms` and the leading factor is `-1`, it checks whether the remainder is still a Mul; if the remainder is NOT a Mul, it takes a shortcut and matches the remainder against the negated expression directly, bypassing the normal two-term decomposition loop; `_matches_simple` handles the case where only a single non-coefficient term exists by dividing out the coefficient; `matches` dispatches between commutative matching via `AssocOp._matches_commutative` and non-commutative matching via `args_cnc` separation — this product pattern-matching logic lives here, not in `exprtools.py` or `operations.py`), and the `_unevaluated_Mul` and `_keep_coeff` helpers. | `numbers.py` | Numeric types hierarchy: `Number`, `Integer`, `Rational`, `Float`, `AlgebraicNumber`, and singleton constants (`Zero`, `One`, `Half`, `NegativeOne`, `Infinity`, `NegativeInfinity`, `NaN`, `ImaginaryUnit`, `Pi`, `Exp1`, `GoldenRatio`, `Catalan`, `EulerGamma`). `Integer.__new__` is the constructor for whole-number symbolic integers — when given a string input, it strips embedded spaces (e.g., `"1 000"` → `"1000"`) before converting via `int()`, and uses an internal `_intcache` dict for caching small integers (with optional tracing via the `int_trace` decorator); this string-space-stripping and integer-caching logic lives here, not in `sympify.py` (which handles general string-to-SymPy conversion but does not perform space-stripping for integer construction). `Float.__new__` is the constructor for arbitrary-precision floating-point numbers — it normalizes string inputs (e.g., prepending "0" to ".5" → "0.5", converting "-.75" → "-0.75"), handles an empty-string precision argument (`prec=''`) that triggers automatic digit-precision detection from the string representation, and converts from various input types (Python float, integer, decimal, mpmath, tuple, Rational) to the internal multi-precision format; this construction and string-parsing logic lives here, not in `evalf.py`. Each numeric type and singleton implements its own rich comparison operators (`__gt__`, `__ge__`, `__lt__`, `__le__`, `__eq__`); e.g., `Infinity`/`NegativeInfinity` define comparison logic that distinguishes finite reals from other unbounded values — when the other operand is real but its finiteness/sign is not fully determined (e.g., a positive symbol not confirmed infinite or finite), the comparison falls through all conditional branches and delegates to the parent `Expr.__le__`/`Expr.__gt__` etc. as a fallback; `Rational` comparisons use cross-multiplication for other Rationals and mpf comparison for Floats, but when comparing against a symbolic real-valued expression (not a concrete Number), they rewrite the inequality by clearing the denominator — transforming `p/q > x` into `p > q*x` — before delegating to the generic `Expr` comparison. The `NaN` singleton has a distinctive `__eq__` that returns True for identity (structural equality: `nan == nan` is True) while `_eval_Eq` returns False (mathematical equality: `Eq(nan, nan)` is False) — this structural-vs-mathematical equality split is defined here, not in `basic.py`. The base `Number` class `__mul__` also handles indeterminate forms: when a zero-valued numeric is multiplied by `Infinity` or `NegativeInfinity`, it returns `NaN` (the indeterminate 0·∞ form); for non-zero values, it dispatches based on sign to return the appropriately signed infinity. `Float._eval_power` handles negative float bases raised to unit-numerator odd-denominator rational exponents (like 1/3, 1/5) by factoring out `(-1)**expt` and computing the power of the positive value, avoiding complex results for cube roots of negatives;
